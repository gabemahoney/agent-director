# User Docs Best Practices

User docs are for the people who install and run agent-director, and for the programs and agents that call it. The README gets a user running in five minutes (rules: "The README" below). Every other user-facing fact lives in exactly one of the files below. "The docs to keep current" and "Write and trim" cover every doc, not only user docs.

## Rules for every user doc

- Keep it short. State each fact once, in the file that owns it, and link to it from anywhere else.
- Current state only. No history, no "used to", no "since release X", no bug IDs. A minimum version a caller checks for is current state and may stay.
- No implementation detail: no source files, functions, packages, spec IDs (SR-x), design reasons or alternatives considered.
- No testing: how the project is tested belongs in `test-writing-guide.md`.
- Concrete, copy-pasteable commands. No code beyond commands, config files and sample output.
- Don't explain common tools (tmux, jq, sqlite3, cron) beyond the exact commands a step needs.
- Error names, fields and states are the contract; advice text is a hint.
- Stay generic: no one client's integration.
- Error cases and recovery go only in `caller-contract.md`, `operator-actions.md` and `maintenance.md`.

## The files

| File | Belongs | Doesn't belong |
|---|---|---|
| `README.md` | What agent-director is, prerequisites, the one-line install, a first spawn, scheduling the sweeps | Everything else |
| `docs/install.md` | Full requirements, every install path and `install.sh` flag, upgrading, the TypeScript client install, uninstall | Using agent-director |
| `docs/usage.md` | Day-to-day use past the first spawn: spawn states, session names, MCP use, the permission relay, templates, pause and resume | Every flag (that is `cli-reference.md`); error handling |
| `docs/configuration.md` | Every `config.toml` key: range, default, what it bounds, when a change takes effect | Why a default was chosen; measurements |
| `docs/maintenance.md` | Scheduling `find-missing` and `expire`; bringing sessions back after a reboot | Hand repair (that is `operator-actions.md`) |
| `docs/caller-contract.md` | Rules for programs and agents that call agent-director: what errors mean, when to retry, the live-row sequence | Steps only a human may take |
| `docs/operator-actions.md` | Human-only procedures: `agent-director-admin`, each refusal that needs a human, and the exact commands to check and fix it | Anything an automated caller may do |
| `docs/hooks.md`, `docs/permissions.md`, `docs/settings.md` | How a spawn's hooks, permissions and settings layer over Claude Code's or Codex's own | Claude Code's or Codex's own reference (link to it) |
| `docs/multi-account.md` | Running a spawn under another Claude or Codex account | General `extra_env` use |
| `pkg/api/README.md`, `pkg/ts-bun-client/README.md` | The Go and TypeScript client APIs | The CLI, install of the CLI |
| `docs/cli-reference.md`, `docs/mcp-reference.md`, `docs/admin-reference.md` | Generated by `make generate` from the verb descriptions | Hand edits: change the description and run `make sandbox CMD="make generate"` |

## Changing user docs

- Put a new fact in the one file whose "Belongs" column fits. If none fits, ask before creating a file, and add it to this table first.
- Before you rename or move a heading, find what points to it. Error text and verb descriptions name headings in `operator-actions.md` and `caller-contract.md`, and the `pkg/api/readme_*_test.go` tests pin their wording.

## The README

`README.md` is for people who want to install and run agent-director: what it is, prerequisites, the one-line install, a first spawn and scheduling the sweeps. A reader should get through it in under a minute and have it running in five. Above all, keep it short and simple: how to install, and how to use.

- No code. Command lines are fine.
- The happy path only: no theoretical error cases or alternative installs.
- No debugging tips, migration or backups.
- Don't point to the extended docs; readers can find them.

## The docs to keep current

- **User docs:** `README.md`, `docs/install.md`, `docs/usage.md`, `docs/configuration.md`, `docs/maintenance.md`, `docs/caller-contract.md`, `docs/operator-actions.md`, `docs/hooks.md`, `docs/permissions.md`, `docs/settings.md`, `docs/multi-account.md`, `pkg/api/README.md` and `pkg/ts-bun-client/README.md`.
- **Generated references:** `docs/cli-reference.md`, `docs/mcp-reference.md` and `docs/admin-reference.md` (see "The files").
- **Architecture:** `docs/architecture.md`, under the rules in `docs/architecture-docs-guide.md`.
- **Developer and operational guides:** `docs/migration-guide.md`, `docs/test-writing-guide.md`, `docs/release-skill.md` and `docs/release-blockers.md`.

The `docs/*-guide.md` files are rules for agents. Idea and Bug work never changes those rules; suggest a rule change to the maintainers as separate work. Do record facts a guide asks for, such as a new schema version's downgrade recipe in `docs/migration-guide.md` §5.

## Write and trim

- Document what readers need to do with the software as it is now; requirements are a correctness check, not an outline to reproduce.
- Use short, plain sentences, and lead with what the reader needs to know.
- Explain each fact in one place and link to it elsewhere, because repeated explanations drift apart.
- Use lists for things that really are lists, and paragraphs for everything else.
- Prefer a small update to an existing document. Add a document only for a distinct reader task that needs its own explanation.
- Remove outdated or duplicated passages and documents. Trimming and deleting matter as much as adding.

Always finish any doc writing or reviewing effort with a succinctness pass: reread what was written and cut every word, sentence and section the reader doesn't need. Be on guard for documentation bloat, because docs grow with every change and each extra line makes the useful ones harder to find.
