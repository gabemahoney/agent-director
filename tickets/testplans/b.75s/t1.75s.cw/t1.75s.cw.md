# Busy send E2, E4, E5 and E6 (b.kii) — `busy-send-claude-wait-turn` testplan

t1 collector for Claude Code as a Covered Agent of the shipped binary (Idea
`b.kii`, Plan `b.xis`; Epic `t1.xis.oo`: Tasks `t2.xis.oo.u8` and
`t2.xis.oo.2o`, Subtasks `t3.xis.oo.u8.sm` and `t3.xis.oo.2o.gv`; Epic
`t1.xis.p8`: Task `t2.xis.p8.zp`, Subtask `t3.xis.p8.zp.gi`; Epic
`t1.xis.wm`: Task `t2.xis.wm.hg`, Subtask `t3.xis.wm.hg.k1`; Epic
`t1.xis.8a`: Task `t2.xis.8a.sv`, Subtask `t3.xis.8a.sv.ga`). It is the one
Claude Docker collector of E2, of E4's Steer Turn, of E5's forced delivery
and of E6's conditional pause. Its cases run under
`make test-docker EPIC=busy-send-claude-wait-turn` with `DRIVER_MODE=shell`,
against the real CLI, operator tool, SQLite, hook process identity, tmux and
processes.

## Driver mode

Every case sources `test/driver/busy-send-claude.sh`. Its agent is the Claude
stand-in `/opt/driver/stand-in-claude/claude`: an interactive bash that is
the row's pane process and, like Claude Code, exits on SIGTERM. The case
plays Claude Code's part: it types each hook with `/opt/driver/pane-hook.sh`,
so every hook is a direct child of the recorded pane process with a pipe, as
Claude Code gives it, for the stream its owned output goes to:
`--stdout-pipe` for `PostToolBatch`, whose steer is stdout
`additionalContext`, and `--stderr-pipe` for every other event, the wake's
prompt being its stderr (each writes only to a stream that takes a write
deadline, which a regular file does not). It runs the owned `FileChanged`
hook itself where Claude Code would after a change of the watched path, and
`PostToolBatch` where a parent or child tool batch would end. It makes no
claim about Claude Code's own intake, watcher, wrapping or hook timing, which
stay with the Managing Intelligence's live qualification on the AD test VM
(Epic criterion 7 of E2 and E5, criterion 6 of E4).

A force call is finite but returns only once its force is decided or its
12-second active phase is over, so case 5 runs it in the background
(`start_call`) while it plays the agent's hooks, and joins it (`join_call`);
the EXIT trap joins a call still running before cleanup and shows its output
when the case failed. `start_call` puts the call under the fixture's own
watchdog (coreutils `timeout`, 60 s, then `KILL` 5 s later), far past the
product's 15-second allowance, which it never shortens: a call still running
then fails the case at either join instead of hanging it. Where Claude Code's watcher would react to the call's
touch of the wake endpoint, the case waits on that endpoint's own change
events (`await_touch`: an inotify watch through node's `fs.watch`, armed
before it looks, bounded at 10 s), never on a timer or a poll. That stands in
for the watcher only; E5's live check on the AD test VM (Epic `t1.xis.p8`
criterion 7, SR-8.3), which the Main Agent runs separately under its own
authorization, owns Claude Code's watcher, intake, compaction, plan Dialog
and timing premises.

Nothing seeds coverage: spawn, reuse and resume record each Launch covered,
with route A and its own wake endpoint, from the binary's covered set
(`{claude}`), as they do in production. Each case checks those recorded facts
before the Launch's `SessionStart`.

Physical no-typing evidence: every tmux call of the case and of
agent-director goes through the call recorder
`/opt/driver/delay-create-tmux/tmux` (`TMUX_CALL_LOG`), which logs each
call's caller. A case passes only if no call by agent-director sent keys or a
paste buffer and the input journal (`input_attempts`) is empty; the only
typing is `pane-hook.sh`'s hook lines and, in cases 2 and 5, the case's own
direct tmux key, which the advice tells the caller to send.
