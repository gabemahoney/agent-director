.01 — unresolved historical cause; initial pre-write guard failure is a strong source-supported candidate.
Original lines 5-13: eight allow decisions, ALL eight delivered_at timestamps, no proven_gone_at, row check_permission. Acknowledgements span 17:50:43.334 to 17:50:44.434 UTC, about 1.1 seconds. Settlement instants span 17:51:07.097-.148. Approval deadlines are settlement minus 4s, so acknowledgements were about 19s before approval expiry. Original trace (lines 16-25) has initialize/session-new/session-prompt and SEVEN permission/plan responses, missing execute (the first request). All later requests receive allow-once/plan-accepted. The peer cannot complete its prompt while execute remains unanswered. It is wrong to infer eight emitted responses from eight delivered_at values: SR5.2 expressly disclaims receipt.

The observed seven-later-responses pattern narrows the transport seam:
* protocol.go writeLoop first guard failure calls done(error), discards that single frame, and CONTINUES. Requests.enqueue's done marks that request terminal; there is no re-enqueue.
* A failure of the second guard, a write timeout/error or partial write instead sets writeFailed and stops/drains the worker. Under normal valid runtime trace semantics, those fatal paths cannot explain successful writes of the following seven frames. Nor can observer execFileSync throwing: it would kill this one Node peer and prevent later trace responses.
* CheckCursorAnswer uses inWriteTx(0). Store boundedConn(0) allows only connGrab=1ms to acquire the single database/sql connection; SQLite BEGIN IMMEDIATE has busy_timeout=0. Main controller operations and async writer guards share that exact Store. A concurrent controller read/ack/admission can therefore cause ErrStoreBusy even while request deadline, durable ack and all runtime/pane authority remain valid. The first writer guard discards the answer permanently on that failure. This is a concrete feasible product interleaving; original logs do NOT record the returned error, so it is not yet a proved historical cause.
* cursorAuthority does not compare row_version, so merely admitting later permissions and advancing row_version cannot itself invalidate the first request. It verifies stable launch/life/session/runtime facts and permits check_permission.
* VerifyPane's multiple 1500ms tmux queries and runtime probes can also fail conservatively in the first guard under load, without transport failure. No pane output or raw guard error was retained, so this remains an alternative. The synchronous committed-SQL observer may affect backpressure/timing, but it cannot on its own establish why a single full answer vanished while later answers were parsed.
* Request retirement/deadline before the first guard remains technically possible if the first response was queued long before the later frames; there are no write-stage timestamps. Early acks alone do not timestamp actual writer completion.

No source fix made: changing guards to wait/retry or relaxing independent evidence without deterministic demonstration would be speculative. In particular DO NOT infer ordinary load latency simply from the passing xtrace rerun, change the 20s wait, remove the missing-execute assertion, replay an uncertain answer, or reinterpret delivered as receipt.

.08 — question-policy failure is excluded by supplied evidence; startup input admission ordering is a concrete race, historical attribution remains probable rather than proved.
Original lines 485-490: row waiting, zero permission rows, peer trace contains initialize and session/new ONLY; NO session/prompt. The configured persistent-fallback question was never generated by the peer. This is not a question-denial deadline failure or evidence of approving persistent policy.

session.go:399 rep.report(SessionStart) starts a hook subprocess which commits public waiting. reporter.report then waits for child exit, rereads row/runtime, and rechecks runtime/pane ownership BEFORE returning. Only session.go:404 arms admission=true. terminalInputLoop takes admission.CompareAndSwap(true,false) asynchronously at Enter receipt and stores accepted=false irrevocably when that bool is false. Thus a public caller can observe waiting, run load_identity and successfully deliver send-keys while report verification is still running; the reader refuses the submitted line even if Run processes its event after it arms admission. No future wait can recover that discarded input. There is an analogous Stop/waiting window at session.go:435-439. Passing rerun adds no proof of failure-stage timing.

This is an observable readiness/order mismatch, not by itself proof that the public send-keys operation promises conversation-level acceptance: send-keys can succeed after typing keys which the gateway refuses. The .08 policy fixture treats public waiting as a complete gateway-readiness barrier. Both product and fixture semantics must be kept distinct.
