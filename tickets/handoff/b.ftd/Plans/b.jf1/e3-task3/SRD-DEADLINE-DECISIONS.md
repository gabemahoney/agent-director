

### E3 Task3 deadline implementation decisions — coordinator

Engineer decisions adopted subject to independent testing and source review; later findings supersede these initial claims. Exact old-code RED and initial unchanged GREEN retained. Historical run09 causes remain unknown.

- api.Decide and Client.Decide start one real context at entry, independently of the injectable relay judge clock. Client includes identity and deferred ad.decide.called within that context; cleanup no longer holds Client's closed-state mutex. Real Store receives an immutable WithContext-scoped handle sharing the existing pool and cleanup lane. Positive max_wait_ms is a hard SQL/reporting context deadline and never extended by subsequent relative waits.
- All bounded store methods intersect their local duration with the original context; acquisition, PRAGMA, BEGIN, query, COMMIT, rollback and restoration use this context. Bounded SQLite busy_timeout is zero. Pure reads and BEGIN use cancellable Go retries, capped both by the context and the original available busy allowance, so a stale positive SQLite busy handler cannot continue after the context.
- Each Store pool has exactly one connection. Connection cleanup owns its lease until rollback/restoration succeeds or Raw(driver.ErrBadConn) disposal completes. One shared cleanup lane has at most one active worker, with queue size constrained by that one-connection pool. It exits on drain. Callers wait for cleanup only until the same context; expired cleanup never starts a background-context rollback. An open transaction or shortened timeout is never returned to another caller.
- COMMIT success remains success despite expiry in later cleanup/reporting/ack reads. Precommit expiration is ErrStoreBusy with no commit attempted. A COMMIT error is an internal unconfirmed-outcome error instructing a durable request read before retry; it is not ErrStoreBusy and does not assert nothing was recorded.
- Cancelable trail.Emit uses one writer worker plus 64 queued events (one additional in-flight event maximum). It preserves FIFO among accepted bounded events, including row_mutation.committed before the same Client call's decide.called. It writes through the existing mutex/file/fsync path, strips tool_input at admission and serialization, and does not spawn replacement workers for blocked I/O.
- Trail Emit returns ErrPending when accepted work outlives the caller context, ErrQueueFull/ErrClosed when admission fails, and actual write/fsync errors when observed in time. Writer.Status exposes Pending, Failed, Rejected and LastError even when existing fail-open callers discard errors. Rejections receive a best-effort aggregate admission_rejected meta event on the same worker once writing resumes. Writer.Close(ctx) stops admission, drains FIFO and closes the worker/file; an expired Close remains explicitly pending.
- Zero-wait compatibility: connection acquisition still gets only the preexisting 1ms connGrab; SQLite lock allowance is zero, without retries. Immediately available SQL gets one fixed 1s execution/cleanup budget, always intersected with an enclosing original context. API MaxWaitMs=0 fixes that allowance once at call entry. A positive call whose absolute deadline has actually expired cannot start fresh SQL, even if its lock happens to be free; permitting unbounded execution afterward would contradict the mandatory overall deadline. Source comments make this distinction explicit.

Limits: context cannot force a descheduled process or uninterruptible native call to return. Pending audit events are not fsync receipts or crash-durable. Worker resource bounds, quarantine safety, FIFO/rejection and actualSQL/cleanup deadline behavior require independent validation.
