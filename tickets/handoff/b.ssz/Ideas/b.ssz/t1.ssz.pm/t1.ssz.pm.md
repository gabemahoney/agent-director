# SRD: Codex support in agent-director (b.ssz)

Companion to PRD t1.ssz.qi (approved). This document states what must be true of the software for the PRD to be met. It does not design the code.

## Scope, baseline and conventions

- **Binding inputs.** PRD t1.ssz.qi; the User's decisions in `tickets/Ideas/b.ssz/t1.ssz.qi/gabe-decisions.md`, except decision 4's "CSCB and the bots must be updated before release", which the User's later answer replaced: migrating CSCB, its bots and the skills is separate work and does not block the release; the technical calls in `tickets/Ideas/b.ssz/srd-design-brief.md`; the TLA+ suite and its verdicts under `tickets/Ideas/b.ssz/tla/` (SR-12); the User's later decisions recorded in b.ssz's body: the Codex login for the real-Codex probe (SR-16.1) and the launch path per agent, an approved exception to parity (SR-5.0); and bug b.nx4 (approved), which moves AD's directory to `~/.config/agent-director` in this release (SR-11.7).
- **Baseline code.** dev/v0.12.0 at `5a05f44` (cited "D") with feature/b.146-relay at `5be84a8` (cited "R") merged into it. feature/b.3ie at `d2d89d3` (cited "S") is part of the baseline only if it is merged when this work starts; every requirement that depends on that says so. b.xjn (Claude subagent visibility) lands before this work; the requirements that depend on its design are gated on its approved SRD (SR-6.8).
- **Parity rule.** A Codex agent under AD does exactly what a Claude Code agent under AD does today; today's code settles every design question, and nothing is added that AD lacks for Claude, except the launch path the User approved as an exception (SR-5.0). Each "as Claude today" fact this SRD relies on is listed in Appendix B as P-n, with file and line pinned to the commits above. Those citations are evidence only: requirements below name modules and identifiers, never lines, and the build must not rely on the cited line numbers.
- **Tracing.** Each subsection names the PRD part it serves and the acceptance criteria, numbered AC-1 to AC-28 in the order they appear in the PRD. Appendix C maps every AC to SRs.
- **Paths.** `tickets/Ideas/b.ssz/` means `/home/horde/projects/agent-director-project/tickets/Ideas/b.ssz/`, the bee's folder. It is outside the repo, and nothing in it is ever committed: what the build keeps there (the TLA+ suite, the probe's and the pre-release check's scripts and results, the breaking-change text) stays there, and what the repo needs from it is copied in (SR-12's vendoring).
- **Terms.** *Agent*: `claude` or `codex`. *Codex folder*: the folder Codex reads its login, rules, hooks and sessions from (`CODEX_HOME`, else `~/.codex`). *Group folder*: a Codex folder named with `CODEX_HOME` in a spawn's or template's `extra_env`. *Pass-through arguments*: the agent's own arguments (today `claude_args`, renamed `agent_args`). *Verified agent process*: the process the hook gate accepts, the row's recorded pane process with its start time (P-3). *End report*: the store's record that the row's verified agent process sent a Codex SessionEnd (SR-3.1, SR-6.5). *Model-checked*: a rule listed in SR-12, whose TLA+ runs and verdicts SR-12.3 records. *Must-win settings*: the per-launch settings of SR-5.2 that no argument may override.
- **RESEARCH NEEDED** marks a fact about Codex that neither the code nor the research settles. Each has a stated fallback (doc only, a named code change, or stop and ask the User) in the RESEARCH NEEDED table, and each is settled by the real-Codex probe that is the build's first step or, at the latest, by the pre-release check (SR-16).

## SR-1: Choosing the agent

Serves: PRD "Choosing the agent", "Errors, renames and upgrade". AC-1, AC-2, AC-3, AC-5, AC-24; bug b.nx4 (`ErrOldLayout`, SR-11.7).

### SR-1.1: The agent input
- `spawn` and `make-template` take an `agent` input on every surface: `agent` on MCP and in the TypeScript client, `--agent <value>` on the CLI, an `Agent` field in the Go library's spawn and make-template parameters, and an `agent` key in a template file.
- The accepted values are exactly `claude` and `codex`, compared case-sensitively, as `relay_mode` values are today (P-11). An empty value counts as not given, as an empty `relay_mode` does.
- No config key, environment variable, store column default or other setting supplies an agent. `config.toml` gains no agent key.

### SR-1.2: How a spawn's agent is resolved
- A spawn's agent is its per-call agent when one is given, otherwise the agent its template names, otherwise none.
- A per-call agent overrides the template's agent.
- A template that names no agent supplies none. On an install that crosses the rename, the upgrade writes `agent` `claude` into every template stored before it that names none (SR-11.2), so those templates keep supplying `claude`; a template made afterwards without an agent supplies none. A template the upgrade did not migrate (one copied in afterwards, or one left by an upgrade made without this release's installer) is refused at spawn with SR-4.3's `ErrTemplateMalformed` naming `agent_args` when it holds `claude_args`, and otherwise supplies no agent, so a spawn that names none gets `ErrAgentMissing`; the upgrade docs say so (SR-15.2).
- `resume` takes only the row id (P-13) and relaunches with the row's recorded agent; it accepts no agent input.
- A spawn with the reuse opt-in on a finished row resets the row to the new spawn's resolved agent; a failed reuse whose restore applies puts the row's previous agent back (P-36).

### SR-1.3: Refusals and their order at spawn
- A spawn checks, in this order, and the first failure is its error; each refusal writes no row, creates no tmux session, pre-trusts nothing and writes no template:
  1. The explicit instance id's control-character check (unchanged, `ErrInvalidFlags`).
  2. Template loading, in this order: today's checks in their order (the name, a missing file, a decode failure, one key under two spellings, unknown keys, then `relay_mode`; P-32), an old key (`claude_args`) being refused per SR-4.3 at the unknown-key check; then a template whose `agent` value is not `claude` or `codex`, `ErrTemplateMalformed`, even when the call gives a valid agent; then a template with a non-empty `agent_args` and no `agent`, `ErrTemplateAgentMissing`, whatever the call gives. This is the relative order of SR-1.4's checks (`relay_mode`, the agent, `agent_args` with no agent).
  3. The cwd checks (unchanged).
  4. The `relay_mode` check (unchanged).
  5. The agent: a per-call value other than `claude` or `codex` is `ErrAgentInvalid`; no per-call agent and no template agent is `ErrAgentMissing`.
  6. Argument ownership: a spawn that would inherit a non-empty `agent_args` from a template whose agent differs from the resolved agent is `ErrAgentArgsMismatch` (SR-2.1).
  7. The resolved agent's refused pass-through arguments: Claude's set as today (P-4), Codex's set per SR-2.3, both `ErrSpawnDeniedFlag`.
  8. Codex only: any `allow`, `deny` or `ask` entry from the call or the template is `ErrPermissionsUnsupported` (SR-5.5).
  9. The `extra_env` checks (unchanged rules, P-10; advice per SR-4.4).
  10. The tmux session name checks (unchanged).
- The relative order of every check that exists today is unchanged (P-11); the new checks sit where listed.
- With this order a spawn with no agent is refused with `ErrAgentMissing` before the `extra_env` checks run.
- The launch path (SR-5.0) adds no check here: a spawn is never refused for an agent's launch path, set or unset, and a malformed `[launch]` value is a config refusal (`ErrConfigMalformed`), made when the config loads, before any verb's checks, as every config refusal is (SR-4.3).

### SR-1.4: make-template
- `make-template` stores the given `agent` and `agent_args` in the template file and stores no `agent` key when none is given.
- `make-template` checks, in this order, and the first failure is its error; every check runs before it creates the templates directory or writes or replaces any file, as its checks do today (P-33, P-61):
  1. The template name (unchanged, `ErrTemplateNameUnsafe`).
  2. `relay_mode` (unchanged, `ErrTemplateMalformed`).
  3. An `agent` value other than `claude` or `codex`: `ErrTemplateMalformed`, as it refuses a bad `relay_mode`.
  4. A non-empty `agent_args` with no `agent`: `ErrTemplateAgentMissing`.
  5. A `codex` template with any `allow`, `deny` or `ask` entry: `ErrPermissionsUnsupported`.
  6. `extra_env` (unchanged rules, `ErrReservedEnvKey`; advice per SR-4.4).
- This keeps spawn's relative order for the same concerns (SR-1.3: `relay_mode`, then the agent, then the permission lists, then `extra_env`). An existing name without the overwrite option is still refused when the file is written (`ErrTemplateExists`), after these checks, as today.
- `make-template` does not check refused pass-through arguments, as today for Claude (P-4).
- The question-tool setting's own deny entry (SR-9) is never an `allow`, `deny` or `ask` entry for these checks.

### SR-1.5: Rows record their agent
- Every row stores its agent, and `get` and `list` show it as `agent` (`claude` or `codex`), as do the Go library's row types and the TypeScript client's result types.
- `status` keeps its result shape.
- Every row that existed before the upgrade reads `agent` `claude` (SR-3.4).

### SR-1.6: New error names
- Six new error names exist: `ErrAgentMissing` (no agent), `ErrAgentInvalid` (a per-call agent value not `claude` or `codex`), `ErrAgentArgsMismatch` (inherited arguments for another agent), `ErrTemplateAgentMissing` (a template with arguments and no agent), `ErrPermissionsUnsupported` (a permission list on a Codex spawn or template) and, for the directory move, `ErrOldLayout` (AD's old directory not yet moved, SR-11.7).
- Each is declared beside the existing errors of its kind (spawn validation errors in `internal/spawn`, template errors in `internal/config`, `ErrOldLayout` beside the store's schema errors in `internal/store`) and re-exported from `pkg/api` under the same name, following the pattern `pkg/api/aliases.go` already uses for `ErrSpawnNotFound` and the tmux errors: a package variable bound to the internal sentinel, with its own doc comment (P-65). A Go caller matches each with `errors.Is` against `api.ErrAgentMissing` and the others. Today's spawn and template errors are not re-exported; the six new ones are.
- Each is catalogued in `pkg/api/errnames` (Catalog, its generated `catalog.json` and the package map in its generator) and keeps the five-way coherence test green (P-44). The first five are listed in the `ErrorNames` of every verb that returns them in `pkg/api/manifest` (`spawn`: all five; `make-template`: `ErrTemplateAgentMissing` and `ErrPermissionsUnsupported`).
- `ErrOldLayout` follows the store's schema errors (`ErrSchemaMismatch`, `ErrSchemaMigrationRequired`) exactly (P-88): `internal/clisetup` re-exports it, `clisetup.NewOpenError` and `OpenError.Is` name it, its catalog entry pairs it with clisetup's sentinel, no verb lists it, and the coherence test's exceptions for names no verb lists take it as they take those.
- Each has an exported error class in the TypeScript client, mapped from its `err_name`, and appears in the client's public-surface golden files. `ErrOldLayout`'s class doc says "the old directory" and links to `docs/install.md`'s Upgrade section, without naming its path.
- Each error's description names what was refused and what the caller does instead; that text is advice, the name is the contract.

## SR-2: Pass-through arguments

Serves: PRD "Pass-through arguments". AC-4, AC-6.

### SR-2.1: Which agent the arguments belong to
- Per-call pass-through arguments belong to the spawn's resolved agent; a template's `agent_args` belong to the template's agent.
- The merge rule is today's (P-6): a per-call list that is supplied replaces the template's list wholesale; an absent per-call list falls back to the template's. On MCP and in the Go library an explicitly empty list is supplied and replaces the template's; on the CLI (nothing after `--`) and in the TypeScript client an empty list counts as not supplied.
- A template's non-empty `agent_args` are inherited only when the template's agent is the resolved agent; when it is not, and no per-call list is supplied, the spawn is refused with `ErrAgentArgsMismatch` (SR-1.3 step 6). A supplied per-call list, an explicitly empty one on MCP and Go included, means nothing is inherited and nothing is refused for this rule.
- `make-template`'s `agent_args` input is `--agent-args` (repeatable, one argument each) on the CLI, as `--claude-args` is today; `spawn` keeps taking its pass-through arguments after `--` on the CLI (P-51).

### SR-2.2: A prompt among the arguments
- A positional prompt among a Codex spawn's pass-through arguments is not refused, reaches Codex as its initial prompt, is stored on the row with the other arguments and is replayed by `resume`, as for Claude (P-5).

### SR-2.3: Refused Codex arguments
- A Codex spawn whose resolved pass-through arguments contain any of the following is refused with `ErrSpawnDeniedFlag`; nothing is written or launched. The description names the refused flag bare, without a value attached to it by `=` or given after it, as Claude's check names it (P-4); for `-c`/`--config`, `--enable` and `--disable` it also names the key path or the feature that made the argument refused (for example `-c` and `hooks.SessionStart`, or `--enable` and `default_mode_request_user_input`); for a subcommand it names the subcommand:
  - **A Codex subcommand in command position.** The first argument before any `--` that is neither an option nor the value of an option that takes one, when it names a Codex subcommand or an alias of one. Every subcommand is refused, under one rule: each picks or resumes another session, runs non-interactively (`login` and `logout` among them) or attaches to a remote or shared service, the PRD's refused categories. The subcommands are a constant list in AD: `agents`, `exec`, `e`, `review`, `login`, `logout`, `mcp`, `mcp-server`, `plugin`, `app-server`, `remote-control`, `completion`, `update`, `doctor`, `sandbox`, `debug`, `apply`, `a`, `resume`, `fork`, `queue`, `archive`, `delete`, `migrate-rollouts`, `unarchive`, `cloud`, `exec-server`, `features`, `help`. The options that take a value are a second constant list: `-c`/`--config`, `--enable`, `--disable`, `--remote`, `--remote-auth-token-env`, `-i`/`--image`, `-m`/`--model`, `--local-provider`, `-p`/`--profile`, `-s`/`--sandbox`, `-C`/`--cd`, `--add-dir`, `-a`/`--ask-for-approval` (RESEARCH NEEDED RN-13 for `-i`'s values). AD reads no Codex help at run time: the probe and the pre-release check compare both lists with the help of the newest and of the minimum Codex (SR-16), and the lists are updated before release; a subcommand that a Codex newer than the release adds is not in the list and passes through. The options `-h`/`--help` and `-V`/`--version` are not refused, as AD refuses no such option of Claude's today (P-4). This bullet is the one statement of the rule; other sections refer to it.
  - **Attaching to a remote or shared service:** `--remote` and `--remote-auth-token-env`.
  - **Overriding AD's hooks, their trust or the typing setting:** a config override (`-c`, `--config`) whose key path, split on `.` as Codex splits it, equals, contains or lies under `hooks`, `tui.disable_paste_burst` or `features.hooks` (so `-c tui={...}` and `-c features={...}` as well), whatever its value; and `--disable hooks`.
  - **Turning the question tool on, only while the question-tool setting is on (SR-9):** `--enable default_mode_request_user_input`, and a config override whose key path equals, contains or lies under `features.default_mode_request_user_input` (so `-c features={...}` as well), whatever its value.
- Every form Codex accepts is recognised: the flag with its value as the next argument, `--flag=value`, and a short flag with its value attached.
- A key path that only shares a prefix string is not refused (for example `-c tui.theme=...` and `-c features.fast_mode=true` pass).
- **`--`.** A `--` passes through unchanged. Codex reads every argument after the first `--` as the prompt (RN-13), so none of them is ever in command position; each is still checked against the refused option forms above, as Claude's check refuses a refused flag wherever it stands (P-4).
- Claude's refused set is unchanged (P-4). Neither agent's set is checked by `make-template` (P-4) or re-checked by `resume` (P-13); at `resume`, AD's must-win settings take precedence over the replayed arguments instead (SR-5.2).

### SR-2.4: Arguments that pass through unchanged
- Codex's permission controls (`-s`/`--sandbox`, `-a`/`--ask-for-approval`, `--add-dir`, `--dangerously-bypass-approvals-and-sandbox`, `--approve-for-me`), its hook-trust bypass (`--dangerously-bypass-hook-trust`) and every other argument not refused by SR-2.3 reach Codex unchanged and in their order, as Claude's permission-skipping argument does today (P-4).

## SR-3: Data model and store schema

Serves: PRD "Choosing the agent", "States", "Errors, renames and upgrade", NFR "Upgrade-safe". AC-2, AC-17, AC-25, AC-26, AC-27.

### SR-3.1: Columns
- The store's columns are renamed: `spawns.claude_instance_id` to `instance_id`, `spawns.claude_args` to `agent_args`, `spawns.claude_session_id` to `session_id`, `permission_requests.claude_instance_id` to `instance_id`, `session_history.claude_instance_id` to `instance_id`, `session_history.claude_session_id` to `session_id`. Each keeps its type, position, constraints, primary key, unique constraints, indexes and the foreign keys that refer to it (`spawns.parent_id`, `permission_requests`, `session_history`).
- `spawns` gains `agent` (text, not null), appended after the last existing column. Its column default, which an added not-null column needs, is the empty string, which is no agent. Every write that inserts or resets a row writes `claude` or `codex` explicitly; a write whose agent is neither fails before writing, and no path relies on the column default.
- `spawns` gains `end_reported_at` (integer milliseconds since the epoch, nullable), appended after `agent`: set when a Codex row's verified agent process sends a SessionEnd (SR-6.5); NULL otherwise, and never set on a Claude row. It is part of the row's raw life that reuse saves and a failed reuse restores (P-36). It is cleared by a later SessionStart from the same agent process (SR-6.5), by resume's move to pending (a failed resume's restore puts it back, with the other columns that move changed) and by reuse's reset. The move to `ended` leaves it set.
- `end_reported_at` appears on no CLI, MCP or TypeScript surface and in no `get` or `list` result. In the Go library it is visible only as the `EndReportedAtMillis` field (0 = none) of the store row type that `pkg/api` re-exports as `Spawn`, as that type shows `IdleSince` and the other internal columns today (P-54); Appendix A lists it.
- Every Claude-named column b.xjn adds, to `spawns` or to a table of its own, is renamed in this same hop by SR-4.1's rule: the hop's tasks find these columns in b.xjn's merged code, and the SR-6.8 addendum records each with its new name.
- No other column, table or index changes. `store_meta` and its store id are untouched.

### SR-3.2: Schema version
- The baseline's schema version is 7 (R; D is 6, S is 8; P-38). This work's hop takes the next version after the newest one merged when the build starts: **v8** on the stated baseline, **v9** when b.3ie's v8 is merged, and one more for each other bee's hop merged first (b.xjn's, if it adds one). The number is checked again when this work merges: if another hop has landed meanwhile, this hop moves to the next free number, with its tests.
- This work takes its own version, as b.146 took v7 over b.kdf's unreleased v6 and b.3ie took v8 over b.146's unreleased v7 (P-38); it does not fold its changes into an earlier unreleased hop.
- `schemaVersion`, `schemaDDL` and the `migrationSteps` registry in `internal/store` move together (the two-places rule of the migration guide): a fresh store is created directly at the new version with the renamed columns and the two new columns, and a migrated store has exactly the same shape.

### SR-3.3: The hop
- One hop from the baseline's version to the new one, in one transaction, following the migration guide's validate-first pattern and the existing sentinel gate (no auto-migration on open).
- It renames the six columns, adds `agent` and `end_reported_at`, backfills `agent` to `claude` on every existing row, and stamps the version as its last statement.
- It is re-entrant: a rename whose new name is already there and whose old name is gone is skipped; a column already added is skipped; the backfill writes only rows not yet backfilled. A run over a store the hop already changed in part ends with the same shape as one clean run.
- A table that holds both an old and a new name of one column, or any other failure, rolls the whole hop back: the store stays at the previous version, byte-for-byte as before, and the open fails as a failed migration does today.
- `ad.schema.migrated` and the other schema trail events are unchanged in name and shape.

### SR-3.4: Data after the hop
- Every existing row keeps every value under the new column names: its id, parent, state, cwd, session name, pass-through arguments, relay mode, transcript path, session id, labels, extra env, timestamps, launch identity, life number, pre-trust choice, launch owner and idle mark (and b.3ie's settle columns when merged).
- Every existing row reads `agent` `claude` and `end_reported_at` NULL.
- Every permission request and session-history entry keeps every value, linked to its row under `instance_id`.
- A migrated row can be resumed: its relaunch is the Claude relaunch with its stored session id and arguments (P-13), and `get` shows its history in `prior_sessions` as before.

### SR-3.5: No downgrade recipe; the way back is restoring copies
- This release adds no reverse recipe to `docs/migration-guide.md` and no test copy of one to `TestDowngradeRecipe_MatchesGuide`'s table; the guide is not edited (PRD non-goal). The way back is SR-11.6's: rename the kept old directory back (it holds the pre-upgrade store, config and templates), restore a store kept outside it from its pre-upgrade copy (with its `-wal` and `-shm` files), then install the previous release with its own installer.
- `TestDowngradeRecipe_MatchesGuide` keeps passing unchanged: it compares only the recipes the guide holds with their test copies (P-39).
- The existing downgrade tests that today take a *current* store back with the guide's recipes and seed or read it with raw SQL under today's column names (`TestDowngradeRecipe_KeepsRowsThenRemigratesToDefaults`, `TestDowngradeV6ToV5_KeepsRowsThenRemigrates`, `TestDowngradeV7ToV6_KeepsRowsThenRemigrates`, and b.3ie's v8 to v7 test when merged) start instead from a genuine store at the newest version the guide has a recipe for (v7, or v8 with b.3ie), built with `makeVersionedDB` and seeded with raw SQL in `migration_fixtures_test.go` under that version's column names. They keep testing every recipe the guide holds, unchanged, and their re-migration runs up through the new hop.
- No test-only reverse of the new hop is written: a reverse recipe belongs to the post-release guide follow-up the PRD names.
- The user docs say so: `docs/operator-actions.md`'s "Back" steps, and any other user doc that names the downgrade recipes, say that restoring the pre-upgrade copies is the only way back from this release's store, and drop the recipe alternative they offer today (P-40). The guide itself is not edited.

### SR-3.6: Reading and writing the new columns
- Every store read and write uses the new column names; outside the migration steps no SQL in `internal/store` names an old column. The existing hops keep their own versions' column names unchanged (SR-13), so `makeVersionedDB` still builds each older version's store as it does today.
- The store refuses to insert or reset a row with an agent other than `claude` or `codex` (nothing written).
- Every hook write, verb write and sweep write that exists today keeps its conditions (gate, snapshot, version) unchanged apart from the column names.

## SR-4: Renaming AD's public surface

Serves: PRD Goals ("agent-generic names"), "This is a breaking release", "Errors, renames and upgrade", "Documentation". AC-25, AC-27.

### SR-4.1: The naming rule
- Every Claude-named name on AD's own surface gets a generic name with no alias: drop the `claude` prefix where the bare name is unambiguous on that surface, else use `agent_`. Appendix A is the complete old to new table; it is binding.
- `session_id` is unambiguous on every surface: AD prefixes every tmux name with `tmux_` (`tmux_session_name`, `tmux_socket`, the trail's `tmux_session_id`), and the trail's existing `session_id` field in `ad.hook.fired` already means the agent's session id. `instance_id` matches the `trail-emit` verb's existing `--instance-id`/`instance_id` (P-42).
- Claude Code's own names (`CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, `.claude.json`, `~/.claude/settings.json`, `--settings`, `--resume`, `AskUserQuestion`) and Codex's own names are not AD's and do not change. `AGENT_DIRECTOR_INSTANCE_ID`, `AGENT_DIRECTOR_RELAY_MODE` and `AGENT_DIRECTOR_LABEL_*` keep their names.

### SR-4.2: Surfaces covered
- The CLI (every verb, and `agent-director-admin`'s `kill-finished` and `delete`), MCP tool parameters and results, the Go library (`pkg/api` and every internal type it re-exports by alias: `Spawn`, `RowSnapshot`, `LiveSpawnIdentity`, `ExpireCandidate`, `PermissionRow`, `SessionHistoryEntry`, and the parameter and result types; `pkg/api/apitest`'s exported helpers), the TypeScript client (parameter and result keys, types, JSDoc, error classes, public-surface goldens), `config.toml` keys, template keys, store columns (SR-3), trail fields of every record written after the upgrade, help text (the manifest's verb descriptions), parameter and field descriptions, error descriptions and advice, the generated references (`docs/cli-reference.md`, `docs/mcp-reference.md`, `docs/admin-reference.md`, regenerated), and the user docs (README, `docs/` except `docs/*-guide.md`, `pkg/api/README.md`, `pkg/ts-bun-client/README.md`).
- Internal identifiers that name Claude Code's own program or files (the `claude` program name, `.claude.json` pre-trust helpers, Claude's refused-flag set) keep naming Claude. Internal identifiers of the generic concepts follow Appendix A wherever they are re-exported; others may.

### SR-4.3: Old names are refused, never dropped
- CLI: an old flag (`--claude-instance-id` on any verb of either binary, `--claude-args` on `make-template`) is refused with `ErrInvalidFlags`, the description naming the new flag; nothing runs.
- MCP: an old parameter key (`claude_instance_id`, `claude_args`) is refused with `ErrInvalidFlags` by the existing unknown-key check (P-34), its description naming the new key; nothing runs.
- TypeScript client: a parameter object carrying an old key (`claude_instance_id`, `claude_args`) makes the call throw the client's `ErrInvalidFlags` class, naming the new key, before any process is started.
- `config.toml`: an old key (`disable_askuserquestion` under `[defaults]`, in any letter case of table or key, as the decoder matches them, P-32) is refused with the existing `ErrConfigMalformed`, naming `disable_ask_user`; every store-backed verb, `serve` and the hook behave as for any refused config today. Unknown keys other than the old ones stay ignored, as today (P-32).
- Template: an old key (`claude_args`, any letter case) is refused with the existing `ErrTemplateMalformed`, naming `agent_args`.
- The Go library has no old names; a caller using one fails to compile.
- No old name is accepted as an alias anywhere, and none is silently dropped.

### SR-4.4: Wording and advice

## SR-5: Launching Codex

Serves: PRD "Installing and launching", "Groups, logins and environment", NFR "Hooks fail open", "No screen text". AC-5, AC-6, AC-7, AC-8, AC-9, AC-11, AC-12, AC-13, AC-14, AC-15.

### SR-5.0: The launch path (both agents)
- **An approved exception to parity.** AD's config gains an optional launch path for each agent (the User, 2026-10-11, recorded in b.ssz and the PRD). It is the one thing this work adds that AD lacks for Claude today, and it changes no other rule.
- **The keys.** A `[launch]` table in `config.toml` holds two optional string keys, `claude_path` and `codex_path`, under one bare-key `[launch]` header, so `install.sh`'s pre-flight line form holds (P-60). As for every config key, names match regardless of letter case, a key set under two spellings is refused, and unknown keys under `[launch]` are ignored (P-32, P-86).
- **Values.** A value is an absolute path, or `~/` followed by a path, which is joined onto `HOME` when the config loads, as `[store] db_path`'s `~/` is (P-78, P-86). An empty value counts as unset, as an empty `[store] db_path` gives its default. Any other value is refused when the config loads, with the existing `ErrConfigMalformed`, its description naming the key and saying the value must be an absolute path or start with `~/`: a blank value, a relative path, `~` alone, `~user/...`, and a `~/` value while `HOME` is unset or empty (never resolved against another home). A value that is not a string fails the decode, as today. A refused value makes every store-backed verb, `serve` and the hook behave as for any refused config today (SR-4.3).
- **Unset.** An agent whose key is unset is launched by its program's name, `claude` or `codex`, found on the PATH of the pane's environment (the tmux server's environment with the launch's `extra_env` over it; P-8, P-45), as `claude` is today (P-1). Nothing is refused for an unset key, and no error name is added. Where that PATH differs from the caller's, the docs recommend setting the launch path (SR-15).
- **Set.** The program the key names (after the `~/` join) is the first element of the pane's command in every launch of that agent (spawn, `reuse_finished`, `resume`), passed to tmux as one argument, unchanged: no PATH lookup and no shell parsing, so a path holding spaces or quote characters runs as written (P-86). The rest of the command is the agent's launch as SR-5.2, SR-5.7 and SR-13 state it.
- **Per launch, from the config in force.** Each launch takes the path from the configuration its process loaded, as it takes the relay window and the help setting (P-28). Nothing about it is stored on the row: `resume` and reuse use the path in force at their launch, not the one at the row's spawn.
- **No other check.** AD checks nothing about the program, at load or at launch: not that it exists, not its version, not whether it is the agent or a launcher (PRD non-goal; P-1). Reading the path makes no file or network I/O (P-50). A path that names nothing gives what a missing `claude` gives today: the row stays `pending` and `find-missing` marks it `missing` (P-1, P-25). A program that breaks the launcher rule (one that runs the agent as a child, such as Codex's npm `codex`, found on PATH or named by the key) gives what such a program gives today: every hook fails the gate, the row stays `pending` and is noted `unreported` past its grace period, and `ad.hook.pane_is_grandparent` names the agent (SR-6.1; P-2, P-25).
- **The installer.** It counts an agent present by its key or by PATH and runs every Claude Code command with the program `claude_path` names when that is an executable file (SR-11.1). It never writes `[launch]`.
- **No model check; new names.** The launch path changes which program a launch starts, not what moves a row or releases a hold, so it needs no model check (SR-12.5). `[launch]`, `claude_path` and `codex_path` are new names, not renames (Appendix A).

### SR-5.1: The program
- A Codex launch runs the program SR-5.0 gives Codex: `[launch] codex_path` when it is set, otherwise the program named `codex`, looked up exactly as `claude` is today: on the PATH of the pane's environment (SR-5.0; P-1).
- AD makes no check of the program at launch: no discovery of a native binary, no version check, no launcher check (P-1, SR-5.0).
- A missing program (no `codex` on PATH, or a `codex_path` that names nothing) ends the launch as a missing `claude` does: the row stays `pending` and `find-missing` marks it `missing` (P-1, P-25).
- A program that runs the real agent as a child (Codex's npm launcher, for one, on PATH or named by `codex_path`) fails the hook gate for every hook (SR-6.1): the row stays `pending` and, past its grace period with the pane process alive, is noted `unreported` (P-25). The docs tell users who installed Codex with npm to set `codex_path` to the native Codex program (SR-15).

### SR-5.2: Per-launch settings on every Codex launch
- Every Codex launch (spawn, reuse, resume) carries, in addition to the pass-through arguments:
  - **No shared service.** Codex's `--no-daemon`: the agent never starts, joins or stops a shared Codex background service, and one already running is left alone and unused.
  - **AD's hooks** (SR-5.3), supplied through Codex's per-launch config overrides.
  - **Trust for AD's own hooks**, supplied per launch as Codex's hook-trust state for exactly those hooks (their trusted hashes), so Codex shows no hook-review dialog for them in any launch, `no_pre_trust` and failed pre-trust included (RESEARCH NEEDED RN-5 for the hash format; RN-23 for whether this per-launch trust state merges with the hook trust the user's and group folder's config already record, or replaces it).
  - **Typing.** Codex's `tui.disable_paste_burst` set true, so `send-keys`' Enter submits at once and multi-line text arrives as one prompt.
  - **The question tool**, turned off for the launch while `disable_ask_user` is on (SR-9).
  - **Folder trust and hook-trust bypass**, only when pre-trust is `ok` (SR-5.4).
- All of them are per launch: none is written into any Codex folder, the cwd, a project's `.codex/` or any other file, and none outlives the agent.
- **Precedence.** The must-win settings are AD's hooks, their trust, the question tool turned off while `disable_ask_user` is on, the cwd's folder trust while pre-trust is `ok`, the paste setting and `--no-daemon`. Each wins over every pass-through argument at spawn and every replayed argument at resume, whatever that argument sets: one SR-2.3 does not refuse (a `projects` override, say) and one stored before the question-tool setting was turned on included. AD places them so that this holds under Codex's resolution of repeated settings, which RN-13 confirms (after the last pass-through option if the last setting wins, before the first if the first wins), and never after a `--` in the arguments, where Codex would read them as the prompt.
- **No duplicate flags.** When the pass-through or replayed arguments already carry `--no-daemon`, or, on a launch whose pre-trust is `ok`, `--dangerously-bypass-hook-trust`, as an option (before any `--`), AD does not add that flag a second time and refuses nothing (RESEARCH NEEDED RN-16 for how Codex treats a repeated flag). A copy that stands after a `--` is prompt text and does not count.
- Composing a Codex launch makes no store write, tmux call, file or network I/O, so a composition failure writes and launches nothing, as for Claude (P-50).

### SR-5.3: AD's hooks in a Codex agent
- AD registers, per launch, a hook entry for each of Codex's SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, PermissionRequest, Stop, Interrupt and SessionEnd events. Whether and how Codex's SubagentStart and SubagentStop are registered is gated on b.xjn (SR-6.8). The help entry of SR-10.1 is separate (below).
- Each of these entries' command is `exec <quoted path> hook --agent codex` (SR-6.1), where `<quoted path>` is the absolute path of the running binary, as Claude's entries run that binary's `hook`. **Quoting rule:** the path is written inside single quotes, and each single quote or backslash in it is written outside the quotes, escaped with a backslash (as `'\''` and `'\\'`), a form bash, zsh, dash and fish all read as the same path. Codex runs the command through the user's login shell (`$SHELL -c`); `exec` makes that shell replace itself with AD's binary, so no process stands between Codex and the hook, the hook's parent is the Codex process, and the gate applies to it exactly as to Claude's exec-form hooks (P-3; RESEARCH NEEDED RN-14, fish's `exec` included). The command is correct for any absolute binary path.
- Tool events match every tool (RESEARCH NEEDED RN-15 for Codex's form of "every tool").
- **The help entry.** With `inject_help_hook` on, AD also registers on SessionStart the help entry of SR-10.1. Its command is `exec <quoted installed path> help`: the installed path, `~/.config/agent-director/bin/agent-director` (SR-11.7) with the home folder expanded, which Claude's help entry also runs as `<installed path> help` in shell form (P-29), quoted by the rule above. It is not one of the `hook --agent codex` entries, carries no timeout of its own, as Claude's carries none, and is trusted per launch by its own hash (SR-5.2).
- Per-hook timeouts: AD's SessionStart entry 600 s, as Claude's, so the SessionStart wait cap stays below it (P-27); PreToolUse and PermissionRequest the effective relay window, as Claude's two entries with a matcher carry it, the PermissionRequest entry also giving it to the hook as its `--timeout` (P-27; RESEARCH NEEDED RN-9 for a lower cap of Codex's own, whose fallback applies to both of these entries); SessionEnd and Interrupt 3 s, the most Codex allows for them; every other event, and the help entry, Codex's default. Each entry's trust hash is computed over the timeout value it actually carries (SR-5.2, SR-14.3).
- AD's entries are added alongside the user's, the group folder's and the project's own Codex hooks, as a separate configuration layer; they never replace or disable them.

### SR-5.4: Pre-trust for Codex
- `pre_trust` keeps its three values and its rules (P-12):
  - `skipped`: pre-trust is off for the launch (the spawn's `no_pre_trust`; at `resume`, the row's recorded choice, which holds for the row's life).
  - `failed`: the launch's `extra_env` sets `CODEX_HOME` to a value that is not an absolute path (relative, `~`-prefixed or whitespace-only), the same rule `ConfigDirUsable` applies to `CLAUDE_CONFIG_DIR`. The launch proceeds, and one warning line names `CODEX_HOME` and its value and says the agent may stop at Codex's folder-trust prompt. An empty `CODEX_HOME` counts as unset and gives `ok`, as an empty `CLAUDE_CONFIG_DIR` does for Claude (P-12).
  - `ok`: every other Codex launch with pre-trust on.
- On `ok`, the launch trusts the row's canonical cwd (the cwd spawn validation canonicalised, P-11) and bypasses Codex's hook review for that launch only, so the user's, the group folder's and the project's hooks run with no review dialog, as an AD-launched Claude agent never stops for hook review. Nothing is written anywhere.
- On `skipped` and `failed`, the launch carries neither: the folder and the user's, group folder's and project's hooks stay as Codex finds them, their recorded trust included (RN-23), and Codex shows its own dialogs for any not yet trusted. AD's own hooks are still trusted (SR-5.2).
- On `ok` the cwd is trusted for the launch whatever the pass-through or replayed arguments set for `projects`: a `projects` override is not refused, and AD's folder-trust entry wins over it (SR-5.2's precedence; RESEARCH NEEDED RN-13 for how Codex combines repeated overrides of one table).
- Pre-trust trusts only the row's canonical cwd. A pass-through argument that moves Codex's working root elsewhere (`-C`/`--cd`, and `--worktree` where the Codex in use has it) is not refused, and Codex may then show its folder-trust prompt for that root; the docs say so (SR-15.3).
- Codex pre-trust takes no lock and waits for none: `[pre_trust] lock_wait_seconds` applies to Claude launches only.
- The folder-trust entry is correct for any canonical cwd AD accepts, a path containing `.`, spaces or quote characters included.

### SR-5.5: Environment, groups and permission lists
- A Codex launch's environment is composed exactly as a Claude launch's (P-8): `AGENT_DIRECTOR_INSTANCE_ID`, `AGENT_DIRECTOR_RELAY_MODE`, one `AGENT_DIRECTOR_LABEL_*` per label, and the template's `extra_env` merged with the call's, passed per session.
- AD sets no `CODEX_HOME` unless the spawn's `extra_env` or template names one, never copies a parent's, and treats `CODEX_HOME` as an ordinary `extra_env` key (not reserved). Codex uses its own default folder unless the tmux server's environment names one, as Claude does today with `CLAUDE_CONFIG_DIR` (P-8).
- Any number of Codex agents may run on one Codex folder at once; AD takes no lock on a folder and checks nothing in it beyond SR-5.4's absolute-path rule.
- A Codex spawned through AD from inside an AD-launched Codex agent, by CLI or MCP, gets only its own composed environment: it is a normal, separate agent whose `parent_id` is the caller's row (P-9).
- A Codex spawn whose call or template carries any `allow`, `deny` or `ask` entry is refused with `ErrPermissionsUnsupported`, its description pointing to the group folder's own Codex rules (`rules/` in the Codex folder) and Codex's own permission controls; `disable_ask_user` is never such an entry (SR-9).

### SR-5.6: Nothing written into Codex folders; logins untouched
- No AD command (spawn, resume, reuse, pause, kill, expire, find-missing, the admin tool, the installer, the uninstaller) creates, changes, moves, links or deletes anything in any Codex folder, the default one included.
- AD never runs a Codex login or logout, and never copies, moves or links a Codex auth file. Codex's own writes into its folder (its sessions, history and counters) are not AD's.

### SR-5.7: The resume launch
- A Codex `resume` launches Codex's own resume of the recorded session (the row's session id, or the earlier session of the visible history whose transcript resume recovered, P-14), with SR-5.2's per-launch settings composed afresh from the configuration in force at resume (relay window, help, question-tool setting), the row's recorded pre-trust choice and `extra_env`, and the row's stored pass-through arguments, placed per SR-5.2's precedence and duplicate rules (RESEARCH NEEDED RN-20 for where Codex's resume accepts the replayed options).
- Resume adds no session-picking argument of its own beyond naming that session.

## SR-6: Hooks from Codex agents

Serves: PRD "States", "Lifecycle, subagents and help", NFRs "b.fmk guarantees", "No screen text", "Hooks fail open". AC-8, AC-13, AC-14, AC-15, AC-16, AC-17, AC-21, AC-28.

### SR-6.1: The gate, and which agent sent the hook
- The hook gate is unchanged for both agents: a hook applies only when its parent process and that process's start time are the row's recorded pane process (P-3). Codex rows get no ancestor walk, no nonce and no environment-based identity.
- Each AD hook process learns the agent of the launch that registered it from its own command line, without reading the payload or the store, and classifies its event by that agent. Every Codex hook entry that runs AD's `hook` verb runs `exec <quoted path> hook --agent codex` (SR-5.3; the PermissionRequest entry with its `--timeout` too; the help entry is not one of them: it runs `exec <quoted installed path> help`, SR-5.3); Claude entries are unchanged and carry no `--agent`, and a hook with no `--agent` is Claude's. The `hook` verb's `--agent` takes `claude` or `codex`; it is listed with the `hook` verb's parameters in the manifest (P-70) and in Appendix A, and it is part of each Codex entry's command, so of its hook-trust hash (SR-5.2, SR-14.3). Any other value is a hook failure, handled as today: fail-open, except a relayed PermissionRequest, which fails closed (P-26). A Claude launch's hooks are classified exactly as today.
- A Codex hook runs through the user's login shell (`$SHELL -c`) with the environment Codex gives it. AD's hooks rely on `AGENT_DIRECTOR_INSTANCE_ID`, `AGENT_DIRECTOR_RELAY_MODE` and the label variables reaching them, and on Codex reading a relayed verdict from a stdout that only AD's hook wrote (RESEARCH NEEDED RN-22 for what shell startup files and Codex's environment policy do to both).
- A Codex started by hand inside an agent's pane, a shared Codex service, a Codex reached through a launcher that does not hand over, and any other process carrying the row's id move no row: their hooks fail the gate and write one `ad.hook.ignored` as today.
- For a pending row's SessionStart refused with `pid_mismatch` whose parent's parent is the pane process, `ad.hook.pane_is_grandparent` is written as today, its advice naming the row's agent's program, the launcher case (for Codex, a `codex` that runs Codex as a child, such as Codex's npm launcher; RESEARCH NEEDED RN-21 for the Codex wording) and the fix: set that agent's launch path, `[launch] claude_path` or `[launch] codex_path`, to the native program or a wrapper that hands over to it (SR-5.0).

### SR-6.2: State mapping for Codex rows
- A Codex row's hooks set these states (model-checked: SR-12, MC-6):
  - SessionStart from the verified agent process: `waiting` (Codex sends it at its first prompt, and at the next prompt after every later session start).
  - UserPromptSubmit, PreToolUse, PostToolUse: `working`, held by an open request exactly as for Claude (the working hold).
  - Stop: `waiting`.
  - Interrupt with no `agent_id` (Esc mid-turn, or cancelling an approval): `waiting`.
  - PermissionRequest: `check_permission` (with `relay_mode` on, the relay of SR-8).
  - SessionEnd: the end report of SR-6.5; no state change.
  - Interrupt carrying an `agent_id`, and any other event: a soft refresh, as unknown events are today (P-19). A marked subagent Interrupt is assumed, not modelled (SR-12.5).
- Only the row's own agent moves a Codex row out of `pending`, and any applied hook of its verified agent process that sets a state does so, as for Claude today (P-62): a SessionStart moves it to `waiting`, a UserPromptSubmit to `working`; a soft refresh and the end report keep the state. Codex's first hooks arrive at its first prompt, so until then the row is `pending`, whether Codex waits for its first prompt, sits at a startup dialog or sign-in screen, or fails the gate; past the grace period with its pane process alive, `find-missing` notes it `unreported` as for Claude (P-25). AD sends no key and approves nothing on its own.
- `ask_user` never appears for a Codex row: a PreToolUse for Codex's question tool sets `working`.
- Claude rows' mapping is unchanged (P-19), and Claude rows get no Interrupt hook.

### SR-6.3: Session id and transcript
- A Codex row's session id is the payload's `session_id`, never a part of its transcript path; a Claude row's stays the transcript path's basename (P-16).
- A Codex row's transcript is the payload's `transcript_path` (Codex's rollout file), recorded under today's presence rule: recorded when the file exists, NULL when it is reported but not yet on disk (P-16).
- No AD path composes a transcript path for a Codex row: not `resume`, not `find-missing`'s heal, not `get`.
- A Codex row whose session id is recorded and whose transcript path is NULL gets its path from its agent's next applied hook that has no `agent_id`, carries the same session id and reports a transcript path that exists. This is the Codex counterpart of `find-missing`'s heal, which skips Codex rows (P-15; RESEARCH NEEDED RN-10).
- That heal is the store's existing transcript heal write (P-57), made by the hook once its own gated write has applied: it applies only while the row's transcript path is NULL and its session id is the hook's, and it writes one `ad.session.jsonl_healed` (`instance_id`, `session_id`, `jsonl_path`, `source` `ad_spawn_store`), the record `find-missing`'s heal writes for a Claude row. Apart from it, an ordinary hook's session record is unchanged: it keeps the path of a row that records a session id (P-57).
- A hook carrying an `agent_id` (a subagent's, SubagentStart and SubagentStop included) records no session id and no transcript path, as today (P-16).

### SR-6.4: Session rotation
- A SessionStart from the verified agent process with a session id different from the row's archives the outgoing session id and its transcript path into the row's session history and makes the new session the row's, in the same transaction, as for Claude (P-17). This holds after Codex's `/clear`, `/resume`, `/fork` and `/new`, each of which Codex reports by a SessionStart at the next prompt (RESEARCH NEEDED RN-6).
- `get`'s `prior_sessions` and `transcript_status`, and `resume`'s use of the visible history, work for Codex rows as for Claude rows.
- Until that SessionStart the row shows the earlier session, and `resume` uses the earlier session (PRD difference).

### SR-6.5: The Codex session-end rule (model-checked: SR-12, MC-1 to MC-5)
- A Codex SessionEnd from the row's verified agent process, for any session id, records an end report on the row and does not change its state.
- **The end-report write** is that hook's one gated write, made as Claude's soft-refresh SessionEnd is today (P-18, P-56): the state kept, the session record handled as for any ordinary hook (P-16), `last_seen_at` set and `end_reported_at` set to the time of the write. Its trail is that write's: one `ad.spawn.state_transition` (`instance_id`, `prior_state` and `new_state` both the row's state, `triggering_event_name` `SessionEnd`, `soft_refresh` true, `source` `ad_spawn_store`) and the invocation's one `ad.hook.fired`, as for any applied hook; nothing else.
- **When a Codex row ends.** The agent's end moves a Codex row to `ended` only when its agent process of the current launch is proven gone by a process check and the row holds an end report. `find-missing` (SR-7.5) and `pause` (SR-7.3; before its keys or in its wait) make this move. With no end report, a gone agent process gives what it gives a Claude row today: `missing` from `find-missing` (P-25). A row `find-missing` marks on tmux evidence alone (its agent process could not be checked) gets `missing` as today, end report or not.
- The other writes that put `ended` on a row are outside this rule, unchanged, and apply to Codex rows as to Claude rows: a plain spawn ending its own new row when its tmux create found the session name held (no agent ever ran), and the restores after a failed resume or a failed reuse, which put a finished row's earlier state back (P-58).
- **The move to `ended`** is `find-missing`'s mark with `ended` in place of `missing` and `decision_reason` `ended` in place of `find_missing` (P-55): one guarded transaction that applies only while the row is in a live state, still holds the launch snapshot that was judged and still holds an end report. It sets `ended_at` and `last_seen_at`, clears the liveness note, its time and the launch start, and advances the row's version; in the same transaction it closes the row's requests that still await an answer (an undecided one denied with `decision_reason` `ended`, the value Claude's terminal SessionEnd uses, so that `decide` on it returns `ErrNoOpenPermissionRequest` as it does for Claude, P-18, P-77; a decided one keeps its verdict) and proves every request of the row gone (`agent_gone`), as Claude's terminal SessionEnd and `find-missing`'s mark do (P-18). A move that does not apply writes nothing, the request close and the trail included. With feature/b.3ie merged, the move also writes b.3ie's settle columns as every terminal write does, so `ended` is reported at once (P-69); the end-report write, which keeps the state, changes neither settle column. A Codex row that `find-missing` marks `missing` (no end report) has its undecided requests denied with `find_missing`, as today.

## SR-11: Installer, upgrade and release

Serves: PRD "This is a breaking release", "Installing and launching", "Errors, renames and upgrade", "Documentation", NFR "Upgrade-safe". AC-10, AC-13, AC-26, AC-27; bug b.nx4 (SR-11.7).

### SR-11.1: Installer pre-flight and agent steps
- **Presence.** `install.sh` requires at least one agent present (with `tmux`, `jq`, `file`, `sqlite3`, and `curl` for `--from-release`, as today). An agent counts as present when its launch path (SR-5.0), as the pre-flight reader reads it, names an existing executable file, or when its program's name (`claude`, `codex`) is on PATH. With neither present the install fails as today (exit 2), naming both agents, their `[launch]` keys and how to install either. Each agent is a presence check only, as `claude` is today (P-30): the installer runs no other check of either program.
- **Claude Code's program.** Every Claude Code command the installer runs uses one program: `[launch] claude_path` when it names an existing executable file, otherwise `claude` from PATH. That covers the summary's version line, `mcp add` for `--register-mcp` and the MCP steps of SR-11.7; `uninstall.sh --mcp-also` runs `mcp remove` with the same program (SR-11.4).
- **Reading `[launch]`.** The pre-flight `config.toml` reader reads `[launch] claude_path` and `codex_path` under the rules it applies to `[store] db_path` (P-60): one `[launch]` header and each key once, all in lower case; a one-line `"..."` value holding no backslash, or a `'...'` value, optionally followed by a `#` comment, holding no control character. A `launch` key or a dotted `launch.` key before any header, a second `[launch]` header, another letter case of the header or a key, or a value in another form stops the install in pre-flight with exit 5 and `install.sh: err_name=ErrConfigMalformed`, naming the line and what to change, before anything on disk changes. A `~/` value is joined onto `$HOME`, an absolute one is used as is, and an empty one counts as unset; any other value (relative, blank, `~` alone, `~user/...`) stops the install in pre-flight with exit 5 and `install.sh: err_name=ErrConfigMalformed`, naming the line, before anything on disk changes, as the new binary would refuse it (SR-5.0). The reader stays in its self-contained marked block, and `dbpathfix`'s drift guard covers the new keys (SR-14.3).
- With Claude Code present the Claude steps run as today: the help hooks in `~/.claude/settings.json` unless `--no-hooks`, and `mcp add` for `--register-mcp` (P-29, P-30), with SR-11.7's changes on the move.
- With Claude Code absent the installer skips the `settings.json` step and prints that it skipped it because Claude Code is not installed; `--register-mcp` prints that registering AD's MCP server with Claude Code was skipped for the same reason and the install goes on to succeed. `inject_help_hook = true` is still merged into `config.toml` unless `--no-hooks`, as today.
- With Claude Code absent the installer also skips its pre-flight check of a symlinked `~/.claude/settings.json` (today an exit 4, P-67), which guards only that file's merge; the `config.toml` link check runs as today.
- **Summary.** The pre-flight summary prints, for each agent, the program it found (its launch path, or the name's PATH lookup) and that program's version line, and names an absent agent as not installed, rather than an unknown `claude`. When an agent's launch path is set but names no executable file, the summary says so, as that agent's launches would end `missing` (SR-5.0); this is the presence check's own test, and nothing more is run.
- The installer registers nothing with Codex, writes no `[launch]` key, and creates, changes or deletes nothing in any Codex folder, whether or not Codex is present. It prints no hint about Codex's npm launcher: telling it apart would need a check the installer does not make (SR-5.0).

### SR-11.2: Config and template migration
- **When it runs.** The whole migration (its reader, its pre-flight refusals and its rewrite) runs only on an install that crosses the rename: a store exists at the path `install.sh` resolves in pre-flight (P-60), and its `user_version`, read in pre-flight with the sqlite3 read the installer's version step uses (P-75), is below this hop's version. `install.sh` holds that version as a constant, and a Go test beside `install_sh_sentinel_path_test.go` fails when it differs from the hop's version in `internal/store`. With no store there is nothing to migrate, and on a store at or above the hop's version the migration has already run: in both cases `install.sh` reads and changes neither `config.toml`'s question-tool key nor any template, so a template made after the upgrade (one with no agent, or one with a multi-line `agent_args` array) survives every later install byte-for-byte. With no store, a `config.toml` that still holds the old key gets the store open's refusal naming the new key (SR-4.3). A store whose version cannot be read stops the install in pre-flight with exit 5 and `install.sh: err_name=ErrVersionUnreadable`, as the version step does today (P-75). An upgrade made without this release's installer (binaries copied by hand) migrates no file; the breaking-change text says to upgrade with the installer (SR-11.6), and a template left with an old key gets SR-4.3's refusal at spawn.
- **The accepted line form.** The migration reads and rewrites only lines in the form `install.sh`'s pre-flight `config.toml` reader accepts today (P-60): blank lines and `#` comment lines; table headers naming one bare key (`[name]`, with blanks before, inside and after the brackets and a trailing `#` comment allowed); and `name = value` lines whose name is one bare key and whose value ends on that line, optionally followed by a `#` comment. A bare key is letters, digits, `_` and `-`. A UTF-8 byte-order mark on line 1 and CRLF line ends are allowed and kept. Table and key names match regardless of ASCII letter case, as agent-director's decoder matches them (P-32, P-60).
- **`config.toml`** is held to that form in every line already: the existing pre-flight readers stop the install with exit 5 for any other line (P-60). The migration renames the `disable_askuserquestion` line under a `[defaults]` header (any letter case of header and key) to `disable_ask_user` in place; its value, comment and spacing and every other byte stay.
- **Each template's top-level part**, the lines before its first table header (the first line whose first non-blank character, after a byte-order mark on line 1, is `[`), is the only part of a template the migration reads or rewrites. Its tables, from that header to the end of the file, are never read or changed: `make-template` writes them with keys quoted wherever a key is not bare (P-74). In the top-level part a `claude_args` line (any letter case) is renamed `agent_args` in place, its value and every other byte kept, and a template whose top-level part has no `agent` key (any letter case) gains the line `agent = "claude"`, inserted immediately before its first table header, or appended as its last line when it has no header (with the file's line ending, after adding a missing final line end). A template that already names an agent keeps it, whatever its value.
- **Pre-flight.** When the migration runs, beside the existing pre-flight readers, so before the binary swap and before anything on disk changes, `install.sh` stops the install with exit 5:
  - with `install.sh: err_name=ErrConfigMalformed` when `config.toml`, under its `[defaults]` header or headers (any letter case), sets the question-tool key more than once in total under the old name `disable_askuserquestion` and the new name `disable_ask_user` (any letter case): both names, or either one twice. The message names each such line and says to keep one, under the new name.
  - with `install.sh: err_name=ErrConfigMalformed` when `config.toml` sets `defaults` as a key before any header (an inline table, `defaults = { ... }`, any letter case) on a line that names `disable_askuserquestion` (any letter case): the migration renames only a line under a `[defaults]` header, so the new binary would refuse the file. This check runs with or without `--no-hooks`; with hooks on, the existing merge check already refuses any such `defaults` key (P-60). The message names the line and says to set the key as `disable_ask_user` on its own line under a `[defaults]` header instead.
  - with `install.sh: err_name=ErrTemplateMalformed` when a stored template's top-level part holds a line outside the form, sets `claude_args` more than once, or sets both `claude_args` and `agent_args` (any letter case). The message names the template, the line and what to change. `ErrTemplateMalformed` joins the names `install.sh` documents for its exit 5 (P-60).
- So, on an install that crosses the rename, no stored template is left unmigrated: each either names an agent already or names `claude` afterwards (SR-1.2), or the install stops in pre-flight with nothing changed. A template the migration never saw (copied in later, or left by an upgrade made without this installer) gets SR-4.3's refusal at spawn when it holds `claude_args`, and otherwise supplies no agent (`ErrAgentMissing` unless the spawn names one); the upgrade docs say so (SR-15.2).
- **Links.** The pre-flight check of a symlinked `config.toml` that today guards only its merge (P-67) also covers every file the migration will change, with or without `--no-hooks`: `config.toml` when it holds the old key, and each template the migration will change. A link that cannot be written through stops the install in pre-flight with exit 5 and that file's `err_name` above.
- **Order.** After SR-11.7's move (when it is due) and the binary swap, and before the first step that opens the store, `install.sh` migrates `config.toml` and every stored template (`templates/*.toml`) in AD's new directory. The gate's store path and every pre-flight read above are resolved in the old directory while SR-11.7's move is due, and in the new one otherwise; every step after the move resolves them again in the new directory (SR-11.7).
- **Backups.** Each file the migration changes is first copied beside itself, keeping its mode, under a name the `config.toml` merge's backups (`config.toml.bak.<YYYYmmdd-HHMMSS>`, P-67) never take: `<file>.pre-agent-rename.<YYYYmmdd-HHMMSS>`, which does not end in `.toml`, so no template lookup reads it. A symlinked file is written through to its target, as the `config.toml` merge does today (P-29).
- **Replacing a file.** The migrated `config.toml` and each migrated template are replaced whole, never edited in place, with their mode kept and a symlinked file written through, as `ad_replace_keeping_mode` replaces the files the installer merges today (P-67): a 0600 template stays 0600.
- **A failed write.** A migration write that fails after the binary swap (a full disk, or permissions changed since pre-flight) leaves that file as it was, keeps every backup and pre-upgrade copy, and stops the install before the store is opened, with exit 1 as the installer's other failed writes end, and a message that names the file and the error and gives the two ways on: fix the cause and run this release's installer again, which completes the migration (it is idempotent), or take the way back (SR-11.6).
- The migration is idempotent: a re-run that crosses the rename again (an install that stopped before its store was migrated) changes nothing in files already migrated and makes no new backup of them.

## SR-12: Model-checked design

**The Codex profile** used in every model: only the events Codex really sends. SessionStart at the first prompt (and, after `/clear`, `/new`, `/resume` or `/fork`, at the next prompt); UserPromptSubmit, PreToolUse, PostToolUse; Stop; Interrupt from the main agent; PermissionRequest with no `tool_use_id`; SessionEnd with reason `other` on `/exit` and possibly for an old session while the agent runs on; no SessionEnd on kill or crash; no idle-prompt Notification; no PostToolUseFailure; every subagent hook carrying an `agent_id`.

### SR-12.1: Rules
- **MC-1, the end report** (SR-6.5): a Codex SessionEnd from the row's verified agent process, for any session id, records an end report on the row and changes no state.
- **MC-2, ended only when gone** (SR-6.5, SR-7.3, SR-7.5): in response to its agent's end, a Codex row moves to `ended` only when its current launch's agent process is proven gone and an end report exists; `pause` (before its keys or in its wait) and `find-missing` make the move; with no end report a gone agent gives `missing` from `find-missing`, as for a Claude row. The writes of `ended` that are not a response to the agent's end (a spawn's end of its own held launch, the restores after a failed resume or reuse) are outside the rule (SR-6.5).
- **MC-3, clear and follow** (SR-6.4, SR-6.5): a later SessionStart from the same agent process clears the end report and, with a new session id, follows the new one, as Claude's rotation does for any new id.
- **MC-4, pause ends** (SR-6.5, SR-7.3; new behaviour, finding F1): `pause` on a waiting Codex row ends with the row `ended`. Today's wait only polls the row's state and never writes it, so a Codex `/exit` would leave the row `waiting` and `pause` would time out. While `pause` waits on a Codex row, each poll also makes `find-missing`'s single-row check of the row's recorded agent process; when that process is gone and an end report exists, the poll writes `ended`, a write that applies only if the launch is the same, the state is live and the end report is still set. A gone process with no end report is left to `find-missing` (`missing`), as today. Before its state rules, `pause` makes the same check and write on any live Codex row whose agent has already exited with an end report, and returns success as for a finished row (SR-7.3). That write is `find-missing`'s single-row write made at another moment: the model's find-missing action (`FM`) is in every run's next-state relation and can fire in any state where its guard holds, so the runs already contain the write at the moment `pause` makes it (`hx_S` with `CxNoEndedWhileAlive`, and `hx_P`); no new run is needed.
- **MC-5, Claude unchanged** (SR-6.5, SR-13): with every Codex knob off each copied model is today's model. For each of the three this is argued by inspection (every changed expression reduces to the original and the added variables stay constant; `tla/README.md`) and confirmed by a knobs-off run that reproduces the exact state count of the Claude run it copies: `hx_eq_Sns` (b.zuj run 4's `ci_H_Sns`, 11,387,737 states), `rx_eq_live` (b.36h's `cond_live`, 109,518) and `r5x_eq` (b.146 round 5's `fin1_time_ub`, 833,740).
- **MC-6, Codex state mapping and report-in** (SR-6.2): UserPromptSubmit, PreToolUse and PostToolUse give `working`, under the working hold; Stop gives `waiting`; a main-agent Interrupt gives `waiting`; PermissionRequest gives `check_permission`. Only the row's own agent moves it out of `pending`, and any applied hook of its verified agent process that sets a state does so, as for Claude today (a UserPromptSubmit moves `pending` to `working`, P-62). A Codex agent's first hook arrives at its first prompt, so until then the row stays `pending`.
- **MC-7, Interrupt as turn end** (SR-8.2): a Codex main-agent Interrupt proves gone (`turn_end`) every request with no `agent_id` recorded before the second its hook started. A subagent's Interrupt must reach AD marked: read as the main agent's turn end, it would release the hold on a main-agent dialog still shown (control `rx_C_subint`; finding F3).
- **MC-8, no tool_ran** (SR-8.2): Codex requests carry no `tool_use_id`, so no `tool_ran` proof or PostToolUse close applies; after an allow on a main-agent request the hold lasts until turn end (Stop or Interrupt).
- **MC-9, subagent hold** (SR-8.2): a Codex subagent's request, allowed or denied, is proven gone only by `agent_gone`; it holds plain `send-keys` and `pause` until the agent ends, and the main agent's turn end never releases it.
- **MC-10, no idle repair** (SR-8.3): `find-missing`'s repair of a Codex row stuck in `check_permission` goes to `working` (no `idle_since` is ever set on a Codex row), and nothing returns a Codex row left `working` to `waiting` on its own: at rest a Codex row reads `waiting`, or `working` written after the main agent's turn ended.

### SR-6.8.1: Why: the facts about Codex's subagent hooks
These facts are the recorded reason for the decision. Each was seen on all three probed versions unless it names the versions it was seen on, or is marked "source" (read from Codex's source, not seen live).
- **C1.** A subagent that the model spawns sends SubagentStart when its thread starts, fresh or forked. It sends SubagentStop at the end of each of its turns, not once when it ends.
  - Both events carry `agent_id` (the subagent's thread id), `agent_type`, the main session's `session_id` and `model`. Neither carries a description, a parent, a tool-call id or a run mode.
  - Sources: the probe's captures; the source (`core/src/hook_runtime.rs`, `run_pending_session_start_hooks` and `run_turn_stop_hooks`).
- **C2.** No Codex hook carries `background_tasks`, so Codex gives no snapshot of running subagents.
  - The spawn tool's hooks depend on Codex's multi-agent tools. Codex's `multi_agent_v2` feature chooses them, and it is off by default (`features/src/lib.rs`).
  - With the default v1 tools, the spawn result carries the child's `agent_id` (seen on 0.156.0). With the v2 tools, it carries none (seen on 0.159.2 and 0.162.1).
- **C3.** SubagentStart's `model` is the subagent session's own model (source).
- **C4.** `stop_hook_active` means what Claude Code's does (source).
- **C5.** Only spawned subagents send SubagentStart and SubagentStop. Codex's `/review` thread (probed), its compaction and guardian threads, and its memory-consolidation sessions (source) send neither.
- **C6.** Codex waits for the SubagentStart hooks before the subagent's first turn (source; the probe's hook order).
- **C7. A subagent that runs again sends no SubagentStart** (source; never probed live). This covers three cases: given more work after a turn, reopened after a close, or brought back after AD's `resume` or Codex's own `/resume`. Each later turn ends with a SubagentStop.
  - Some later turns do send marked hooks. With the v1 tools, the work arrives as user input, which fires a UserPromptSubmit carrying the subagent's `agent_id` (seen on 0.156.0; source `inspect_pending_input`). A turn that runs a tool fires PreToolUse, PostToolUse and PermissionRequest carrying it (seen on all three).
  - A v2 message to a subagent fires no hook (source). So a turn on the v2 tools that runs no tool sends nothing until its SubagentStop.
- **C8.** Every subagent hook's parent is the Codex process, so it passes the gate as the agent's own (probe).
- **C9. No hook when a subagent is stopped or closed.** When the main agent interrupts a subagent with the v2 `interrupt_agent` tool, no SubagentStop follows (probe, 0.162.1). Whether a v1 interrupt or a close (`close_agent`) sends anything was not probed. Esc sends the subagent's SubagentStop about 10 s later (probe).

So AD cannot tell, from what Codex sends:
- whether a subagent is working or idle (C1, C7);
- whether one is still there after a close (C9), or after AD's `resume` or a Codex session change (C7);
- anything about a tool-less v2 turn (C7).

Any state the view showed for a Codex subagent would either be false at some moment, or need an `unknown` state. The User chose neither.

### SR-6.8.2: The rule: Codex rows show no subagents
- **Registration.** No Codex launch (spawn, reuse, resume) registers SubagentStart or SubagentStop. A Codex launch's AD hook entries are the eight `hook --agent codex` entries of SR-5.3, the help entry while `inject_help_hook` is on (SR-5.3, SR-10.1), and the question tool's deny entry while `disable_ask_user` is on (SR-9, as built in Epic 4 under the probe's Q1 answer).
- **The tracking flag.** Every launch write stores `subagent_tracking` 0 for a Codex launch and 1 for a Claude launch: `InsertPending`, `MoveToPending` and `ResetForReuse`.
  - This matches X-SR-9's meaning: 1 only when the launch's settings register the agent's subagent start and stop events.
  - A failed launch's restore writes back the value the row had before (X-SR-9).
  - In B this is `subagentTrackedParamSQL` and `subagentTrackedColumnSQL` in `internal/store`, and it becomes a requirement here.
- **`list-subagents` on a Codex row** returns `tracked` false and `subagents` `[]`, on every surface (CLI, MCP, Go, TypeScript).
  - `list-subagents` shows only the current life's records (SR-6.8.9), and a Codex life writes none. So a Codex row shows no record, also when it was reused from a Claude row that had some.
  - No error is added: a Codex row is answered as any untracked row is (X-SR-11). The User confirmed on 2026-10-12 that the verb stays answering on Codex rows, with no new error.
- **No Codex hook writes a subagent entry or opens a claimable launch.** Two guards each ensure it on their own:
  - **The classifier.** A hook run with `--agent codex` (SR-6.1) never feeds subagent capture. (A Codex hook entry an operator registers by hand without `--agent` is classified as Claude's (SR-6.1); for that hook only the flag guard below applies.) A Codex SubagentStart or SubagentStop that reaches AD anyway is a soft refresh (SR-6.2) with no entry write. That happens, for example, from a hook entry an operator registered by hand in a Codex folder. A Codex Stop takes no snapshot. No Codex tool hook opens a claimable launch or writes an entry. In B, this is the classifier's `SubagentCapture` flag, set only for Claude.
  - **The flag.** Entry writes need the row's `subagent_tracking` to be 1 (X-SR-3.1), and a Codex launch stores 0.
- **The closes.** X-SR-8.1's close still runs in each write that ends or restarts a Codex row's launch, the move to `ended` included. On a Codex row it finds no running entry and no claimable launch. Unchanged.
- **Claude.** Every b.xjn rule applies to Claude rows unchanged.

### SR-6.8.9: Resume continues the last agent's latest session; no resume across a switch
**The rule (Gabe, 2026-10-12, his simplest statement, the one to write):** "Resume always continues the last agent's latest session. Switching agents without resume is fine. The one thing you can't do is resume across a switch: e.g. Codex runs and ends, then a Claude launch with --resume on the same id." The rest of this section is how AD keeps it.

Gabe (the User) gave his final rule in Slack on 2026-10-12. It replaces this section's earlier text of the same day ("every call shows the current life", and a `list --parent` limited to the parent's life), which was never built:
1. **A new life happens only when the agent type changes** (Claude to Codex or Codex to Claude on the same id): "if you switch Agents that's a fresh start. If you launch a new Agent with or without --resume thats the same 'life'."
2. **Subagent records belong to a life.** They never carry across a switch, and they carry across launches of the same agent.
3. **AD-agent children are not tied to a life.** A switch neither hides nor stops them; `list --parent` still lists them.
4. **Gabe's added rule:** a switch gives up resume of everything before it, permanently. A switch back is a new life, not a return to the earlier one: there is no path from Claude to Codex and back to Claude that resumes the old Claude sessions.
5. **Gabe's resume rule:** `resume` always resumes the latest session of the current life, nothing older. Older sessions stay listed in the session history, but AD offers no way to resume them.
6. Cross-agent reuse stays supported. Codex rows show no subagents. "Calls show only the current life" applies to life-scoped data only: session history and subagent records. `list` is not historical.

The PRD amendment records it as Decision 3. A small TLA+ model checked it before this text was written (below, "Model check").

#### Terms
- **A life** of a row runs from the write that begins it to the write that begins the next. A plain spawn's insert begins the first life. A reuse's reset (`ResetForReuse`) begins the next **only when it switches the agent**. A same-agent reuse, `resume` and the agent's own session changes continue the current life. A failed reuse whose restore applies (`RestoreAfterFailedReuse`) puts the pre-reuse agent and life back (P-36).
- **Life-scoped data** are the row's session history (`prior_sessions` and `transcript_status`) and its subagent records (`list-subagents`).
- **Not life-scoped:**
  - the row's columns: each call shows their current values, and a reuse writes them as today;
  - permission requests: they belong to a launch, and a reuse deletes them as today (B `ResetForReuse`);
  - children: other rows that name this id as `parent_id`.
- **A call** is a verb on any surface: the CLI, MCP, the Go library, the TypeScript client and the admin tool.

#### Reuse across agents
- **The rule.** A spawn with the reuse opt-in on a finished row may resolve to either agent. The row takes the resolved agent.
- **SR-1.2's last bullet and SR-7.6 stand, as SR-6.8.0 amends them.** A reuse takes the new spawn's agent, writes its pass-through arguments and `extra_env`, clears the end report, and stores the new launch's `subagent_tracking` (SR-6.8.2). A failed reuse whose restore applies puts every one of them back (P-36).
- **Already built in B.** `ResetForReuse` writes `fresh.Agent`, and the reuse path takes the spawn's resolved agent.
- **Old rows.** A row from before the upgrade records `claude` (SR-3.4). It may be reused as either agent.
- **Unchanged:** a template whose `agent_args` belong to the other agent gives `ErrAgentArgsMismatch` (SR-2.1); spawn-again advice (SR-4.4); SR-1.6's error names. No error is added, and Appendix A gains no error name (its new rows are SR-6.8.0's). SR-1.3's order is unchanged; only step 7's outcome changes, for resume arguments on a reuse that switches the agent ("Where the decision is taken" below).

#### The life rule (changes B)
- **The reset.** `ResetForReuse` advances `life_number` by one only when the row's stored agent is not exactly the reuse's agent, compared in the reset's own statement. A stored value that is neither `claude` nor `codex` (a hand edit) counts as a switch. Otherwise `life_number` is unchanged. Everything else the reset does is as in B: it archives the current session in the life it ran in, deletes the row's permission requests, closes running subagent entries and deletes claimable launches, and advances `row_version`.
- **A switch back is a new life.** `life_number` only grows: a switch writes one more than the current value, and nothing else changes it but an applied restore after a failed reuse, which puts back the life that reuse left. So a switch from Claude to Codex and back to Claude gives the row a third life, and neither `prior_sessions`, `list-subagents` nor `resume` ever reaches a session or a subagent record from before a switch, however many switches follow (Gabe's added rule; TLA+ `SwitchForgets`).
- **The restore** is unchanged: it writes the pre-reuse `life_number` and agent back from `RawLife`.
- **Which session `resume` relaunches.** The row's current session: the latest the agent reported (set by its SessionStart, replaced at a rotation, cleared by a reuse). Whether the agent can reopen it is up to Claude or Codex. AD adds no choice: `resume` still takes only the id (below).
- **Old stores.** Lives recorded before the upgrade stay as recorded: the hop rewrites no `life_number`. A same-agent reuse made before the upgrade started a new life under the old rule, and its earlier sessions stay hidden. That is coarse, not false.
- **The pre-trust choice.** Every reuse writes its own `no_pre_trust`, as in B, and `resume` keeps it. B's texts that hold the choice "for the row's life" (SR-5.4's `skipped` outcome, P-12, architecture.md's `no_pre_trust` column, and `docs/usage.md`'s "holds for every `resume` of the id"); resume's Description and its `pre_trust` field read as "Help size" below gives (the field: "…because the row's latest spawn turned it off with no_pre_trust") read "until the next spawn or reuse", since a same-agent reuse no longer starts a life (the PRD amendment changes the PRD's pre-trust bullet the same way).
- **What does not depend on the life number.** The conditional writes are guarded by the row snapshot, which includes `row_version` (B `internal/store/rowsnapshot.go`), and every launch writes a new launch token. So a same-agent reuse that keeps the life lets no stale write land. `pause`'s launch key (B `pkg/api/pause.go`, token and life) still changes at every reuse through its token.

The permission requests the reset deleted stay deleted (B `RestoreAfterFailedReuse`). #### Resume continues the latest session only (changes B)
- **The rule (Gabe's resume rule).** `resume` relaunches the row's current session, the latest of the current life, and nothing older. Example: Claude session A runs and ends; the id is reused for Claude without resume, and session B runs and ends; `resume` continues B, never A. Older sessions stay listed in `prior_sessions`; agent-director resumes none of them.
- **The gap in B.** B's `resume` falls back to an older session: when the current session's transcript is not found (the persisted path, then the recomputed one), it walks the visible history newest first and relaunches the first older session whose transcript exists (B `pkg/api/resume.go`, from b.v2c AC6, hardened by b.5jm). Under the rule that fallback is removed.
- **After the change.** `resume` tries only the current session's candidates: the persisted `jsonl_path`, then, for Claude, the path recomputed from the row's cwd and `CLAUDE_CONFIG_DIR`. When neither exists it refuses, with nothing written:
  - `ErrJsonlNeverWritten` under B's condition, unchanged: the row's `jsonl_path` is empty and the visible history is empty. So it still means "nothing was written in this life", which `transcript_status` (`never_written`) and CSCB's reading of it ("no history lost") rely on;
  - `ErrJsonlMissing` otherwise, its list of tries holding only the current session's (sources `persisted` and `fallback`, never `history`). It now also covers a row whose visible history has a transcript that B would have resumed: the caller is told, and agent-director resumes nothing older. This is a meaning change for the breaking-change text (SR-6.8.7);
  - a row with no current session still gets `ErrNoSessionId`, as in B.
- **What it also settles.** b.fmk split history by life partly so that resume's fallback could not reach a session from before a reuse that moved the row's folder (b.fmk final review, S1). With no fallback, `resume` never relaunches a session other than the current one, which the row's current folder wrote, so no folder check is needed. The model shows both sides: `lr_C_nofolder` (B's fallback with a same-agent life) breaks `ResumeOpens`, `lr_lim_b_nofolder` shows B was safe only because every reuse started a new life, and the design, with no fallback, passes.
- **Callers.** CSCB's lost-transcript diagnosis reads the tries' source tokens (`persisted`, `fallback`, `history`); it will no longer see `history`, and a row whose latest transcript is gone is refused with `ErrJsonlMissing` where B would have resumed an older session. Also, after a same-agent reuse whose new session wrote no transcript, the earlier session stays in the visible history, so `resume` gives `ErrJsonlMissing` (B: `ErrJsonlNeverWritten`) and `transcript_status` reads `rotated` (B: `never_written`): CSCB's no-transcript step (`noTranscriptReuse` in its `session-manager.ts`) then runs its lost-transcript diagnosis and reports `fresh-after-amnesia` (or, when the diagnosis is inconclusive, `fresh-after-inconclusive-amnesia`) instead of `spawned` on each later restart of a persona never messaged since its reuse; and where that diagnosis returns `inconclusive` (fungible mode, a mentions channel, DMs on, or no archive configured; CSCB `jsonl-persistence-check.ts`), it records a startup error and posts a Slack notice ending "An operator should investigate" on every such restart (`session-manager.ts`). An optional AD-side fix (give `ErrJsonlNeverWritten` when no transcript of the current life exists on disk, statting earlier sessions only to classify, never to relaunch) would remove that; it is put to Gabe, and this text does not assume it. Recorded in the breaking-change text (SR-6.8.7); the orchestrator tells CSCB.
- **A Codex row with nothing to try.** A Codex row with no recorded `jsonl_path` and a non-empty visible history now gets `ErrJsonlMissing` with no tries; its message says that no transcript path is recorded for the current session (Codex's path comes only from its hooks).

#### Resume arguments, and the key case (Gabe, 2026-10-12, as corrected)
**The key case.** Claude runs and ends, then Codex runs and ends, then Claude is launched on the same id with `--resume`. Gabe first asked for a refusal, then corrected it the same day: **it is not an error. agent-director starts Claude fresh, and `--resume` resumes nothing. The one hard rule is that agent-director never resumes the old Claude session**: that agent would have a gap in its memory, knowing nothing of the Codex period. The same holds for any reuse that switches the agent and asks to resume, either way round.

- **What B does today in this exact case** (a reuse of the finished Codex row naming Claude, with a resume argument in its pass-through arguments):
  - `--resume <old Claude session>`, `--resume=<…>` or `--continue`: refused with `ErrSpawnDeniedFlag` naming the flag, before anything is written (`internal/spawn/validate.go`). Under the corrected rule this refusal is wrong: it must be a fresh start.
  - `-r <old Claude session>`: not refused (bug b.d6q). The reuse switches the row to Claude, and Claude is launched with `-r`; when the old session's transcript is still in the row's folder, Claude resumes it: exactly the forbidden outcome, reported as a successful spawn.
  - `-c`: not refused (b.d6q). Claude continues its most recent conversation in the row's folder, which is the old Claude session when no other Claude conversation ran there since: the same forbidden outcome.
  - The other way round (Claude ran last, a reuse naming Codex with `resume <id>` or `fork`): refused with `ErrSpawnDeniedFlag`, "codex subcommand resume: … picks or resumes another session" (`internal/spawn/codexargs.go`). Under the corrected rule, also a fresh start.
  - `resume <id>` cannot be asked for the other agent: it relaunches the row's own agent. But it replays the row's stored pass-through arguments (B `internal/spawn/relaunch.go`), so a stored `-r <old>` or `-c` (possible today through b.d6q) would steer every later `resume` to that session.
- **Bug b.d6q is folded into Epic 5** (required by Gabe's hard rule and the resume rule; the orchestrator is told): without it, a same-agent reuse after a fresh switch back (Claude, Codex, Claude, then Claude again with `-r <first Claude session>`), a plain spawn, or a replayed stored argument could still reopen an older or pre-switch session. The model's control `lr_C_samepick` shows it.
- **The resume arguments**, one constant set per agent in `internal/spawn` (`ResumeArgs`): every option that picks, resumes or forks an existing session, or that only works together with one of those. The set is read from each agent's own argument parser (not its `--help`, which hides options), at each agent's documented minimum (Claude 2.1.280, Codex 0.156.0) and at its newest version, in a throwaway container before any code, and recorded with those versions beside the probe answers.
  - **Claude**, known at Claude Code 2.1.280: `--resume` and `-r`, with their value when one is given; `--continue` and `-c`; `--fork-session`; `--from-pr` with its optional value; `--teleport` with its optional session (it resumes a teleport session); and the hidden options that require `--resume` or `--continue` (`--resume-session-at <id>`, `--resume-drops-turn <id>`, `--rewind-files <id>`, `--reply-on-resume`), with their values. `--session-id` is not in the set: it names a new session and fails on an id in use, so it never resumes one.
  - **How a Claude argument is read.** An argument exactly equal to a refused long name, or that name with `=` and a value, is matched wherever it stands, as B matches today. Everything else is read as Claude's parser reads it, from the table of Claude's options and how many values each takes (required, optional, list), which the same container check reads from the parser together with the set (as `codexValueLong` does for Codex): a value of an option is never read as an option (`--model -c` and `--append-system-prompt "-concise answers"` pass); `--resume`, `-r`, `--from-pr` and `--teleport` take the next argument as their value when it does not start with `-`; in a short-flag cluster Claude reads `-c`, `-p`, `-h` and `-v` as flags and any other letter as an option whose value is the rest of the cluster, so `-rS1` is `-r S1`, `-cd` is `-c` then `-d`, `-dc` is `--debug c` and `-nrocket` is `--name rocket`. A cluster is a resume argument when, read that way, it holds `-c` or `-r`. An option missing from the recorded table (one a newer Claude adds) is read as a flag that takes no value, so a following `-c` is still read as `--continue`: the safe side. When an exact long-name match is, by the option table, another option's value (`--append-system-prompt --resume foo`), it is refused with `ErrSpawnDeniedFlag` on every path, a switching reuse included, never dropped, so no option is left to swallow the next argument (a test case pins it).
  - **Codex**, known at 0.159.2: the `resume` or `fork` subcommand in command position, with its own options (`--last`, `--all`, `--include-non-interactive`) and, unless `--last` is given, the session id that follows. What Codex reads as the resume prompt after them is kept as the launch's prompt, placed after a `--` so that it is never read as a subcommand; the agent's argument check then runs on the rest, as on a plain spawn.

#### Subagent records follow a life
- **Schema.** In the v9 hop and `schemaDDL`: `subagents` gains `life_number INTEGER NOT NULL` after `stopped_at_source`, the row's `life_number` at the entry's insert, never changed after. The key `UNIQUE(instance_id, subagent_id)` becomes `UNIQUE(instance_id, life_number, subagent_id)`; its index serves the per-row read, the per-launch transitions and the cap (X-SR-10.1). No backfill: the table is new in v9. A store migrated to v9 by an earlier build of this unreleased work is not supported.
- **Writes.**
  - The one entry insert (B `insertEntry`) writes the row's `life_number`, read in the same insert-select as `launch_token`.
  - The one entry read every entry write goes through (B `readEntry`) finds only an entry of the row's current life. An event for a subagent id that only an earlier life holds is handled as an id with no entry: a SubagentStart, a launch result with status `async_launched` or `completed`, and a main-agent Stop listing create a new entry; a SubagentStop, a SubagentStop listing and a launch result with another status write no entry (a launch result still closes its claimable launch). The earlier entry is never changed.
  - Within a life, b.xjn's rules are unchanged, a same-agent reuse included: the reset closes the running entries (`agent_gone`), the entries stay, and a later SubagentStart for the same id reopens its entry and moves it into the current launch (b.xjn's RN-2 answer).
  - Unchanged: the closes (X-SR-8.1) of every running entry of the id; the reads already limited to the current launch (the snapshot's candidates, the launch request's check, the Stop's skip read); the gate (X-SR-3.1); the eviction.
- **Retention.** The cap of X-SR-10.3 counts all the row's entries, every life. An earlier life's entries are all closed and none changes after the switch, so (closed observations, then closed records, oldest `activity_at` first, ties to the lowest `created_seq`) no record `list-subagents` shows is evicted while an earlier life's entry remains, unless the host clock was set back.
- **The read.** `ListSubagentRecords` returns only the entries whose `life_number` equals the row's, in one statement (the join gains `sa.life_number = sp.life_number`). `tracked`, the order and the fields are unchanged.
- **A failed reuse.** Its restore writes the pre-reuse `life_number` back, so the earlier life's records show again. No entry of the failed launch can exist: the restore applies only while the row is still pending at the reset's version, and no hook writes a pending row with no pane (X-SR-8.1).
- **The stable id.** `(instance_id, subagent_id)` identifies a record among those `list-subagents` shows, which are one life's. b.2qh acknowledged this on 2026-10-12 (SR-6.8.7).
- **Why tag, not clear.** Clearing at a switch would lose the earlier life's records for good, and a failed reuse's restore, which writes the `spawns` row only, could not put them back. Tagging keeps them in the store, shown by no call, until the cap evicts them or the row is deleted. It is how b.fmk keyed session history (`session_history.life_number`).
- **What it settles.** A Codex row reused from a Claude row with records shows `tracked` false and `subagents` `[]` (SR-6.8.2). A Claude row reused from a Codex row shows only records its own hooks write. A Claude row reused as Claude keeps showing its earlier records, closed.

#### Docs
Each fact goes in the doc that owns it (SR-15.1; `docs/user-docs-guide.md` gives spawn, pause and resume to `docs/usage.md`, error cases to `docs/caller-contract.md`). Docs state current behaviour only (P-63).
- **`docs/usage.md`:** Gabe's rule in his words, in its own short paragraph near the top of "Pause and resume": resume always continues the last agent's latest session; switching agents without resume is fine; you cannot resume across a switch, with the case "Claude runs, then Codex, then a Claude launch with --resume on the same id", in which `--resume` resumes nothing and Claude starts fresh. "Naming the agent": a reuse may name either agent. "Pause and resume": a reuse with the same agent keeps the row's earlier sessions (`prior_sessions`) and subagent records; a reuse that switches the agent starts afresh, with none shown. **Stated plainly, in its own short paragraph:** switching an id between agents gives up resume of everything before the switch, for good; switching back is a fresh start too, so Claude, then Codex, then Claude again can never resume the first Claude sessions through agent-director. Whether the agent can reopen even its latest session is up to Claude or Codex; children stay listed under `list --parent` either way; `resume` continues only the latest session, never an older one, and older sessions are listed but cannot be resumed. The `list-subagents` text: records are kept across `resume` and a same-agent reuse, and start empty after a switch; the stable id is among the records shown; retention counts hidden records; "When an agent is tracked": also after a switch from Claude to Codex, and an agent predating subagent tracking becomes tracked when it is next resumed or reused as Claude.
- **`docs/caller-contract.md`:** an undone reuse shows the earlier agent, sessions and records again, while its deleted permission requests stay deleted; the sentence "the old conversation is unreachable for good" reads that `resume` continues only the latest session, so an older one is never resumed by agent-director, and never after a switch, a switch back included; a reuse that switches the agent and carries resume arguments drops them and starts fresh, with no error; the caller sees spawn's `dropped_args` (and, on the CLI, the stderr line).
