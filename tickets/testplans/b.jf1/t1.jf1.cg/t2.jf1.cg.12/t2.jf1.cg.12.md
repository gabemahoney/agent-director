# Test case: Concurrent useful work after correlated rejection

Maps Task 3 AC1, PRD AC12 and SR-7.1/SR-9. Reuses case 11's shared driver and
fixtures; no copied lifecycle/error matrix.

## Setup

Same private three-launch environment, designated selector observations and
independent useful worker as case 11. No Cursor account or authentication is used.

## Steps

1. Establish successful correlated useful work from A/B/C and worker overlap.
2. Exercise the current foreign hook claim against B's real outstanding permission,
   verify no target mutation, and complete B's legitimate operation.
3. Configure A's next actual prompt reply as a correlated synthetic auth rejection,
   submit it, and wait for `status` to show `waiting` with the sanitized
   `failure_reason`. Verify A's exact gateway/runtime identities remain alive,
   its binding is unchanged, and only the two intended prompts were received.
4. Submit a second prompt with the same correlated rejection. Wait for owned
   gateway/runtime death, `missing` and the same `failure_reason` on `status`.
5. Complete subsequent B/C and independent worker operations. Check exact results,
   actual selected artifacts and unchanged runtime/binding/starttime identities.
6. Perform B's actual session rotation, replay the captured obsolete hook claim,
   require unchanged row/binding/request/history and complete current B work.
7. Check final exact method counts and clean up only the owned processes.

## Pass criteria

For b.ivj D1/D2, the first rejection ends only A's turn. Its `status` returns
`waiting` and `failure_reason` exactly
`Cursor ACP session/prompt failed: authentication required; check the selected runtime's existing login`,
matching its one `ad.cursor.turn_failed` record with no `ad.cursor.failed` yet.
The second consecutive rejection ends A's session: both owned processes are gone,
`status` is `missing` with the same reason, and exactly one `ad.cursor.failed`
follows the turn-failure record. The peer's raw message is never the reason.
No fallback selection, fresh-session retry or replayed prompt: A receives exactly
one `initialize`, one `session/new` and three `session/prompt` requests, with prompt
texts `before-a`, `affected-rejection` and `affected-second-rejection`, in order.
Peers and independent worker remain useful. Observed JSON and
per-launch artifacts preserve causal correlation. This scripted rejection proves
AD failure handling only; real invalid/expired credentials, renewal, policy repair,
cross-account workers and platform acceptance remain unproven. Scheduler execution
is required; local author checks parse code and never execute this case.
