# Epic 9 — `epic-09-resume` testplan

t1 collector for Epic 9 (`t1.8op.js` — Resume terminated Spawns).
Each t2 is a plain-English case the Docker harness executes. The
Epic 9 Progression Contract requires every t2 to pass under
`make test-docker EPIC=epic-09-resume`.

## Sourced from

- Epic ticket: `t1.8op.js` (Acceptance Criteria #1–#3).
- SRD §7.5 (parent_id derivation), §8.1 (resume verb), §8.2 (JSONL
  slug rule), §13.1 (error catalogue).
- resume-11: SRD SR-20.9 (AC-RES-18, AC-RES-11) and SR-22.1 (`pending`
  means a launch — spawn, reuse or resume — in progress whose agent has
  not reported in).
- Epic 8 (`t1.h98.xw`): SRD SR-22.9 (a hook moves a row only when its
  parent process is the row's recorded pane process) and SR-20.9 (the
  Docker cases type hooks into the pane of a stand-in `claude`).

## Driver mode

All cases are written for `DRIVER_MODE=shell`. Each t2 body has a
single fenced ` ```bash ` block the driver executes after the
per-case DB-reset fixture.

The cases use real `spawn` to create the row + tmux session, but
drive state transitions by synthesizing hook payloads (the Epic 3
pattern). The JSONL file is hand-created at the path
`JsonlPath(cwd, claude_session_id)` resolves to so the resume
pre-flight Stat succeeds.

A hook moves a row only when the `agent-director hook` process is a
direct child of the row's recorded pane process (SR-22.9), so these
cases never pipe a hook from the case's own shell (such a hook is
ignored as `pid_mismatch` and leaves the row as it was). Instead
(SR-20.9; the pattern is described in full in the epic-03-spawn
collector `t1.75s.qo`):

- The hook cases (`resume-1`, `resume-2`, `resume-7`, `resume-8`,
  `resume-11`) run every `spawn` and every `resume` as
  `PATH=/opt/driver/stand-in-claude:$PATH agent-director …`. tmux looks
  `claude` up on the PATH of the process that runs the create (it
  replaces the session's PATH with the client's, so `--extra-env PATH=…`
  would still start the real Claude Code), and finds the stand-in
  `claude` (`test/driver/stand-in-claude/claude`) first; it `exec`s an
  interactive bash, which becomes the pane process agent-director
  records. It never sends a hook by itself.
- `/opt/driver/pane-hook.sh <id> '<payload json>'`
  (`test/driver/pane-hook.sh`) types `agent-director hook < <file> >
  <out>; echo $? > <rc>` into the row's recorded pane with
  `tmux send-keys`, waits (bounded) for the exit status, prints the
  hook's stdout and exits with the hook's exit status. It reads the
  row's `pane_id` when it runs, so after a `resume` it types into the
  pane the resume created.

`resume` itself moves a finished row to `pending` — a launch in
progress, keeping its session id and history — before it creates the
session. The row becomes `waiting` only when the agent reports in, which
in these cases is a synthesised SessionStart.

## Notes for the orchestrator

- Audit standard (SRD §17): run `make test-docker EPIC=epic-09-resume`
  yourself, inspect the JSON stream case-by-case.
- In the hook cases, the resumed tmux session runs the stand-in
  `claude` (an interactive bash), which never reports in, so the resumed
  row stays `pending` until a case types a SessionStart into its pane
  (resume-11 also unsets `ANTHROPIC_API_KEY` and
  `CLAUDE_CODE_OAUTH_TOKEN` as a second guard). `resume-3` to `resume-6`
  send no hook and use no stand-in; only `resume-3` launches anything
  (its spawn starts the real Claude, which never reports in). The cases
  inspect `tmux has-session` and the row's store state — not any
  conversational state.
- Case 6 deliberately recreates a stale tmux session under the
  canonical name to provoke the collision check. The case cleans up
  the stale session at the end so it doesn't leak into later cases.

## tmux session sweep

Cases that exercise real `spawn` leave `cd-*` sessions; the db-reset
fixture cleans them between cases.
