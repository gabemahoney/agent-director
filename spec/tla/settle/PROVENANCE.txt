spec/tla/settle/ provenance

What this is
  Bee b.3ie's TLA+ model of the settle time. It models how status, get and
  list derive the settled state, and how each store write path sets the
  columns that derivation reads. The model is B3ieSettle.tla. With it come
  its 32 cfgs, the scripts that wrote and checked its scheduler jobs, the
  job table, the job ids, the verdicts, the job directory of the
  pass_tchange_before rerun and one local sanity run. Bee b.3ie owns the
  model and its results. The files are vendored as the record of the model
  checking done before b.3ie's product code.

Not wired into make tla
  Nothing in the repo runs these files. `make tla` runs ci/suite.tsv only,
  and ci/run_ci.sh never reads settle/. To run a cfg again, build a job
  context the way gen-jobs.sh does and submit it to the job scheduler.
  job-pass_tchange_before-long/ is one such context, as it was submitted.

Source
  Bee b.3ie, directory tickets/Bugs/b.3ie/ of the ticket tree
  (outside this repo). Copied byte for byte with cp on 2026-10-10. Each
  file was checked equal to its source with diff at copy time. After the
  rerun came back, verdicts.txt was copied again (the bee folder's copy had
  two new lines), and job-pass_tchange_before-long/ was copied whole with
  cp -a and checked with diff -r. job-ids.txt and job-ids-long.txt were
  diffed again and had not changed. The pin list below has their SHA-256s.

Layout (the bee folder's relative layout)
  B3ieSettle.tla          the model
  README.md               the design modelled, the invariants, the
                          mutations and the findings
  cfg/*.cfg               one cfg per scheduler job (32)
  gen-jobs.sh             wrote cfg/ and the job directories
  verify-jobs.sh          checked the job directories without running TLC
  job-README.md           the job table, with the expected verdicts
  job-Dockerfile          the job image file of each job
  job-ids.txt             the 32 scheduler job ids
  job-ids-long.txt        the job id of the pass_tchange_before rerun
  job-pass_tchange_before-long/
                          the rerun's job directory, as submitted (see
                          "The rerun's job directory")
  verdicts.txt            the verdict line of each job, then the rerun's
                          verdict line and the ALL 32 MATCH line
  tla-logs/sanity.cfg     the local sanity run's cfg
  tla-logs/runsanity.sh   the script that ran it
  tla-logs/sanity.log     its log
  PROVENANCE.txt          this file
  gen-jobs.sh, verify-jobs.sh and tla-logs/runsanity.sh name the bee
  folder and the b.3ie worktree by absolute path. They are kept as written,
  as a record. They do not run from here as they are.

Not vendored
  The 32 first-run job directories, job-<cfg>/ for each cfg. gen-jobs.sh
  wrote them. Each holds copies of files vendored here or in spec/tla/,
  plus the two-line `runs` file gen-jobs.sh writes. Also not vendored:
  b.3ie.md, impl-plan.md, settling-state-decision.md and
  job-ids.txt.notes.

Job image files
  tlcjob.sh: the tlcjob.sh in every job directory is byte-identical to
  spec/tla/jobs/lib/tlcjob.sh (cmp and sha256sum, 2026-10-10). The
  first-run job directories are not vendored, so their copies are not
  either. The rerun's directory is vendored whole, its copy included.
  tla2tools.jar: the jar in every job directory is byte-identical to
  spec/tla/tla2tools.jar (cmp and sha256sum, 2026-10-10). Its SHA-256 is
  that jar's pin in spec/tla/PROVENANCE.txt. TLC2 Version
  2026.09.23.154203 (rev: 4260e47). The rerun's directory holds one copy.
  B3ieSettle.tla and the cfg in every job directory are byte-identical to
  the vendored B3ieSettle.tla and cfg/<cfg>.cfg. The Dockerfile in each of
  the 32 first-run job directories is byte-identical to job-Dockerfile.
  The rerun's Dockerfile is not (see "The rerun's job directory").
  Git stores a byte-identical file as one blob, so the rerun's copies of
  the jar, tlcjob.sh, B3ieSettle.tla and the cfg add no new blobs. Only
  its Dockerfile and `runs` do.

The rerun's job directory (job-pass_tchange_before-long/)
  The context the rerun was submitted from, copied whole from the bee
  folder on 2026-10-10 (cp -a, then diff -r). Its six files, each checked
  with cmp on 2026-10-10:
    B3ieSettle.tla           equal to settle/B3ieSettle.tla
    pass_tchange_before.cfg  equal to settle/cfg/pass_tchange_before.cfg
    tla2tools.jar            equal to spec/tla/tla2tools.jar
    tlcjob.sh                equal to spec/tla/jobs/lib/tlcjob.sh
    Dockerfile               job-Dockerfile, except line 9
    runs                     the first run's `runs`, except line 2
  How it differs from the 32 generated job directories:
  - Its name. gen-jobs.sh names each directory job-<cfg>/. This one is
    job-pass_tchange_before-long/, and gen-jobs.sh does not write it.
    job-ids-long.txt names the job pass_tchange_before_long.
  - Its Dockerfile's ENV line (line 9) raises the caps:
      generated  ENV XMX=8g DIRECT=1g BUDGET=3000 DISKCAP_MB=8000
      rerun      ENV XMX=24g DIRECT=4g BUDGET=20000 DISKCAP_MB=60000
  - Its run cap. `runs` line 2 is "B3ieSettle pass_tchange_before
    @19800" (5.5 h). The first run's is "@2900".
  Everything else in it is the same as in the first run's
  job-pass_tchange_before/ (diff -r of the two bee-folder directories,
  2026-10-10).

Local sanity run (tla-logs/sanity.log)
  The design at T = 2, MaxTime 3, MaxWrites 3, with every invariant. It ran
  once, on 2026-10-10, in a local container of the job image's base
  (eclipse-temurin:21-jre) with a 900 MB memory cap. It used
  spec/tla/jobs/lib/tlcjob.sh and spec/tla/tla2tools.jar. Result: PASS,
  158,868 distinct states, depth 12, 6 s.

Wording
  The vendored b.3ie files keep their own wording. Everything else in this
  file follows the repo's wording rule.

Pin list
  One line per vendored file: SHA-256, two spaces, the path relative to
  spec/tla/settle/ (sha256sum format). PROVENANCE.txt is not pinned.
  test/tla/provenance_test.go checks that every other file under settle/
  has a pin line with its SHA-256, and that every pin names such a file.
