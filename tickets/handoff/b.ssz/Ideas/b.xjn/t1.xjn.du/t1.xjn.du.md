# SRD: agent-director tracks subagents via Claude Code hooks

Idea b.xjn. PRD t1.xjn.th (approved). This SRD states what must be true for the PRD to be met. It does not plan the work.

## How to read this SRD

- **Inputs.** The PRD; the real-payload probe, `tickets/Ideas/b.xjn/probe/findings.md` (cited Q1 to Q5 and F1 to F13; logs in `probe/out/v2.1.280/`, `probe/out/v2.1.296/` and, for the foreground follow-up, `probe/out/v2.1.280-fg/`); the TLA+ check, `tickets/Ideas/b.xjn/tla/README.md` (its "Design refinements after the runs" included), `tla/verdicts.txt` (the verdicts, the TLC run times, and the note that the model's header comment was corrected after the runs, comment only) and the model, `tla/src/Phase5HookSub.tla`; the design brief, `tickets/Ideas/b.xjn/srd-design-brief.md`; the decisions on review rounds 1 to 6, `tickets/Ideas/b.xjn/review-round1-decisions.md` to `review-round6-decisions.md`; and the contract agreement, the follow-up notes to b.2qh and the settled items, `tickets/Ideas/b.xjn/contract-and-settlements.md`. The brief is followed except where "Departures from the design brief" says otherwise. Every decision of the six rounds, every settled item and the User's answer to U-1 (2026-10-11), within the bounds round 5's M-1 sets, are applied.
- **Change log.** Where each of them is applied: `tickets/Ideas/b.xjn/srd-change-log.md`.
- **Baselines.** D is dev/v0.12.0 at c7d0f46, the baseline. R is feature/b.146-relay at 5be84a8 (schema v7, the relay rework). S is feature/b.3ie at d2d89d3 (R plus schema v8, the settle time). An untagged requirement holds on every baseline. A tag [D], [R] or [S] marks what differs on that baseline; [R+S] means both. A tag follows the code present when the work is built, not a branch name: an [R+S] rule applies to any build whose code contains R's (dev with R merged included), an [S] rule to any that contains S's, and a [D] rule only to code without R's. User-doc placement follows docs/user-docs-guide.md wherever that file exists, so a build of dev with R or S merged still puts the user-facing facts in docs/usage.md (SR-16).
- **Evidence.** Appendix A lists each code fact this SRD relies on, with file and line at the commits above. The citations are evidence only: requirements name modules and identifiers, never lines, and the build must not rely on the cited lines.
- **Names.** Every new name is agent-neutral: no new table, column, field, parameter, type, method or value contains `claude_`, and no new manifest text names an agent. Codex support (b.ssz; its SRD t1.ssz.pm, SR-6.8) then has nothing of this work to rename or reword.
- **Agent scope.** Agent-neutral, holding for any agent b.ssz adds: the gate on entry writes, terminal rows and clocks (SR-3.1, SR-3.4, SR-3.5); the key and the launches (SR-4.1); what an observation is and how it is kept (SR-4.2's last two bullets); the bound on stored strings (SR-5.3); the record fields, times and invariants (SR-6.1, SR-6.2, SR-6.5); the unknown rule (SR-6.4's first bullet); the closes from liveness (SR-8); the tracking flag (SR-9); the `subagents` table, the schema hop and retention (SR-10.1 to SR-10.4); and the verb (SR-11). Claude Code's: the probe and the narrowings (SR-1); registration and classification (SR-2); each hook's transaction (SR-3.2, SR-3.3); which events create and confirm entries (SR-4.2's first two bullets); teammates, internal agents and claimable launches (SR-4.3 to SR-4.5, and their table, SR-10.5); the payload fields (SR-5.1, SR-5.2); each field's sources (SR-6.3, and SR-6.4's second bullet); the transitions (SR-7); and the fixtures (SR-15.1, Appendix B). SR-12 to SR-17 are cross-cutting: their rules are agent-neutral, and the hooks, tests and docs they name are Claude Code's instances. Where an agent-neutral requirement names a Claude Code event, field or value, it states Claude Code's instance of its rule. Another agent's events, fields, sources and confirmation rules are defined by that agent's own SRD (b.ssz for Codex).
- **Terms.** An *entry* is one stored subagent row: a *record* (confirmed as a subagent, SR-4.2, and returned by `list_subagents`) or an *observation* (unconfirmed, never returned). A *claimable launch* is an internal note of an Agent tool call not yet matched to a subagent (SR-4.5); it is not an entry and is never returned. A *claim* is a start's taking of a claimable launch: it confirms the start's entry and fills no field (SR-4.5). The *current launch* is the row's `launch_token` at the moment of a write; an entry *belongs* to the launch in its own `launch_token` (SR-4.1). *Receipt time* is the instant the agent-director hook process started (SR-6.2). A *live* row is in any state but `ended` or `missing`. A payload field is *supplied* as SR-5.1 defines it (present, not null, of its JSON type and, for a string, not empty); an event that carries a field supplies it, and one with no such field does not. A *main-agent Stop* is a Stop with no `agent_id`. A `background_tasks` entry *lists* a subagent when its `type` is `subagent`, its `status` is `running` and its `id` is a non-empty string. The *launch request* of a subagent is its PreToolUse(Agent); its *launch result* is its PostToolUse(Agent).
- **Out of scope** (PRD non-goals): any hub, transport or UI; transcript parsing; exit status; any permission or relay change (no subagent event becomes a relay proof); changes to `get` or `list`; tracking in-process teammates; storing nesting depth; any action on a subagent.

## Departures from the design brief

1. **Missed launches have unknown start times.** The brief gave a record created from a Stop snapshot "start times = now". The PRD says such a record "holds what the snapshot provides; everything else is unknown", and that no field is inferred (N13 narrows "what the snapshot provides": a listing's `description` is not kept). Its `first_started_at` and `started_at` stay null until a start arrives; an internal opening time drives the snapshot grace rule instead (SR-7.1, SR-7.4, SR-7.5, SR-10.1).
2. **Entry writes need a tracked launch.** The brief adds the tracking flag but does not gate writes on it. A launch from before the upgrade still fires PreToolUse, PostToolUse and Stop, which run the upgraded binary at the same path, so without the gate it would get records; the PRD requires none for that launch (SR-3.1, SR-9).
3. **Failed-launch restores restore the tracking flag.** `RestoreAfterFailedResume` and `RestoreAfterFailedReuse` make an earlier launch current again, so they write the tracking flag back. They close nothing: no entry of the failed launch can exist (SR-8.1, SR-9).
4. **`tool_response.prompt` is content.** Every PostToolUse(Agent) in the probe carries it, teammates' included; it joins the never-read list (SR-5.2).
5. **CLI shape.** CLI flags come only from manifest parameters, so the verb is `agent-director list-subagents --instance-id <id>`, not a positional id. `instance_id` is the agent-neutral parameter name `trail-emit` already uses (SR-11.1).
6. **Docs location.** docs/user-docs-guide.md keeps README.md to install, a first spawn and the sweeps, so wherever that guide exists (D, and dev with R or S merged) the user-facing record facts go to docs/usage.md. On R or S alone, which predate that split, they go to README.md (SR-16).
7. **Time precision.** Times are stored as integer milliseconds, as `launch_started_at` and R's v7 instants are. Whole seconds would make the 2 s grace rule wrong (SR-6.2).
8. **No array, no snapshot.** A Stop or SubagentStop whose `background_tasks` is absent or not an array is not a snapshot and closes no entry (SR-5.1).
9. **Fields apply even when the state does not move.** Every event applies its fields by precedence, also when it changes no state (a SubagentStart on a running entry), so the result does not depend on arrival order (SR-6.3).
10. **Vendoring in place.** `spec/tla/ci/run_ci.sh` runs only its three named spec modules, so the checked model is vendored as an in-place extension of `spec/tla/Phase5Hook.tla`, as b.66h extended `Phase4.tla` (SR-14.2).
11. **One entry per subagent across launches.** The brief keyed entries by (instance id, launch token, subagent id). They are keyed by (instance id, subagent id), with the launch token a field, so the pair is the stable id b.2qh asked for, and a subagent resumed in a later launch stays one record (SR-4.1).
12. **Snapshots close background records only.** The brief let a snapshot close any running entry of the launch. Foreground subagents are never listed (F12), so a snapshot closes only entries whose run mode is background (SR-7.5).
13. **Claimable launches.** The brief confirmed an id only from its launch result or a listing, and a running foreground subagent has neither until it finishes. Its launch request opens a claimable launch, which its SubagentStart claims. The claim only confirms the entry, so the subagent shows while it runs; it fills no field, so every field but the type stays null until the launch result (SR-4.5, N10, N11).
14. **Finished launches close, and times do not depend on the order.** The brief let a launch result never change an entry's state, let a repeated start change nothing, and kept the first start received. A `completed` launch result stops its entry, and a SubagentStop's receipt time then replaces the result's `stopped_at`; a start or an `async_launched` result fills unknown start times, and `first_started_at` is the earliest of their receipt times (SR-6.5, SR-7.1 to SR-7.3).
15. **Listings never describe, and type only what they create.** The brief let a snapshot's `description` fill an unknown description. No listing's `description` is stored: it is Claude Code's own label, which can be prompt text or `(resumed)`, while a record's description is the launching call's own (N13, "Contract agreement"). A listing's `agent_type` is used only when that listing creates the entry, so interleaved listings cannot change a record (SR-6.3, SR-7.4, SR-7.6).
16. **Hidden entries go first at the cap.** The brief deleted the oldest closed entry, record or observation alike. A closed observation, which no verb returns, is deleted before any closed record, so hidden entries never push out the records a consumer sees (SR-10.3).

## SR-1: Probe findings and the PRD narrowings

### SR-1.1: Facts the design rests on
Claude Code 2.1.280 (the README minimum) for every scenario; 2.1.296 has the same fields, plus `tool_response.canContinueAgent` (F10). The probe ran a real, authenticated Claude Code on a private HOME and a private tmux server in throwaway containers; its foreground follow-up ran 2.1.280 the same way, with background tasks disabled (`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`).
- Every subagent hook (SubagentStart, SubagentStop, a subagent's tool hooks, teammates' hooks) has the agent's `claude` process as its parent, so it passes the gate as the agent's own (F1).
- SubagentStart carries `session_id`, `transcript_path`, `cwd`, `prompt_id`, `agent_id`, `agent_type` and `hook_event_name`, nothing else: no description, model, tool-call id, parent or run mode (Q1).
- SubagentStop adds `permission_mode`, `stop_hook_active`, `agent_transcript_path`, `last_assistant_message`, `background_tasks` and `session_crons`, and has no status or exit reason (Q1). Every probe stop had `stop_hook_active` false; Claude Code sets it true on a stop that follows one a stop hook blocked (its hooks reference).
- A PostToolUse(Agent) fired inside a subagent carries that subagent's `agent_id`, and its `tool_response.agentId` is the child's id; a launch by the main agent carries no `agent_id`. SubagentStart never carries the parent (Q2).
- The launch request, PreToolUse(Agent), carries the call's `tool_use_id`, `tool_input.description` and `tool_input.subagent_type` (and the launcher's `agent_id` when nested). It comes about 20 ms before the launch's SubagentStart, for background and foreground launches alike; in the foreground follow-up no hook came between them (F13), and a background launch's result can (F2). A teammate spawn's PreToolUse(Agent) carries `tool_input.name`; the subagent launches observed do not (F13; `fg.jsonl`, `s3.jsonl`, `s9.jsonl`, `s10.jsonl`).
- For a background launch, PostToolUse(Agent) and SubagentStart fire 0.07 to 2 ms apart (receipt times in the probe logs), in either order. Claude Code waits for SubagentStart hooks before the subagent runs, so a subagent's stop is never received before its start's hook has run (F2).
- For a foreground launch, PostToolUse(Agent) fires once the subagent has finished, after its SubagentStop. Its `tool_response` has `status` `completed`, `agentId`, `agentType`, `resolvedModel`, token and tool counters, and content fields; a nested one carries the launcher's `agent_id` (F11). An `async_launched` result has no `agentType` (`s3.jsonl`).
- A subagent restarts under the same id whenever it is woken: a parent once per finished child, a teammate once per message (F3).
- Every subagent hook carries the main session's id; after `/clear` it carries the new session's id, also for a subagent started before it (F4).
- In-process teammates: PostToolUse(Agent) has `tool_response.status` `teammate_spawned` and no `agentId`; SubagentStart and SubagentStop fire per message with one stable `agent_id`; the snapshot lists the teammate with `type` `teammate` and a different id. SubagentStart alone cannot tell a teammate from a subagent (F5).
- `tool_input` never shows the run mode; `tool_response.status` does: `async_launched` for a background launch, `completed` for a foreground one. With background tasks enabled, every probe launch ran in the background, `run_in_background: false` included, consistent with a fork gate on for that login; with them disabled, every launch ran in the foreground (F6, F11).
- The model is `tool_response.resolvedModel` (F7, F11).
- Claude Code's internal agents fire a SubagentStop with `agent_type` "" for an id never started, and tool hooks with an `agent_id` and no `agent_type`; neither follows a SubagentStart or a PostToolUse(Agent) (F8).
- TaskStop and "Exit and stop tasks" send no SubagentStop; `/clear` interrupting a running subagent does (Q3).
- The Stop hook's `background_tasks` entries are `{id, type, status, description, agent_type}` (a teammate's has no `agent_type`). Only `status` `running` was seen; a finished or killed task is absent. It lists every background subagent running in the process, nested ones included, across a `/clear`; a subagent between its SubagentStop and its next SubagentStart is not listed; a resumed subagent's description is `(resumed)` (`s10.jsonl`), and a teammate entry's is the start of its prompt (`s9.jsonl`): an entry's `description` is Claude Code's own label for the task, not the launching call's `description`. SubagentStop also carries `background_tasks`, and a background subagent's lists the stopping subagent itself as running (Q4). Foreground subagents are never listed, by a Stop or by a SubagentStop (F12).
- No hook shows a subagent's exit status. A launch that fails before a subagent exists gives its PreToolUse(Agent), then a PostToolUseFailure(Agent) with the same `tool_use_id`, and no SubagentStart (Q5; `s10.jsonl`).

### SR-1.2: Narrowings of the PRD
Each is implemented by the requirement named, and tests assert the narrowed behaviour.
- **N1 Identity.** A record is identified by (instance id, subagent id), not by (session id, subagent id): hooks after `/clear` carry the new session id (F4). The record keeps the session id of the event that created it, and stays one record across the agent's launches (SR-4.1, SR-6.3).
- **N2 A start opens an observation.** A SubagentStart opens an unconfirmed observation, which becomes a record once a payload confirms the id is a subagent: the start's claim of a claimable launch (SR-4.5), its launch result, or a listing. So a subagent whose start claims one shows at once, and a teammate is never confirmed or shown, N10's residual aside (F5, F13; SR-4.2, SR-4.3).
- **N3 A snapshot covers background subagents, process-wide.** A Stop snapshot covers every running background entry of the current launch: all sessions, nested ones included. An entry whose run mode is foreground or unknown is never closed by a snapshot; its stop, its launch result or liveness closes it (F12). The PRD edge case "a snapshot from the new session does not close records of the old one" is narrowed: after `/clear` the new session's snapshot closes an old-session background record only when that subagent is absent from it, that is, no longer running (Q4; SR-7.5).
- **N4 Stopped tasks.** A subagent killed with TaskStop, or ended by "Exit and stop tasks", sends no stop event; its record becomes `lost` through the next snapshot (a background one) or liveness (Q3; SR-7.5, SR-8).
- **N5 No exit status; run mode from the launch result.** No record says how a subagent ended (Q5). The run mode comes from `tool_response.status`, or is `background` from a listing (F6, F11, F12; SR-6.3).
- **N6 "Any order" means every order Claude Code produces:** launch results at any point relative to start and stop, and hooks of different subagents interleaved. A stop is never received before its own start (F2), and a launch request is received before its start (F13). A stop with no recorded start is a lost start: the stop changes nothing, and its listing still applies (SR-4.4, SR-7.2).
- **N7 Docs.** The PRD's "README.md and docs/architecture.md" maps, on D, to docs/usage.md, docs/hooks.md, the generated references and the client READMEs, plus docs/architecture.md (SR-16).
- **N8 Content scope.** The no-content rule covers everything this feature reads and writes. A relayed PermissionRequest's `tool_input`, which the relay already stores, is existing relay behaviour and out of scope (SR-5.2).
- **N9 Kill.** The PRD acceptance criterion "killing an agent ... turns each of its running records to lost" is narrowed: `kill` writes no row state, and the SessionEnd a killed agent sends (reason `other`, F9) does not end the row. A killed agent's running records turn `lost` when its row is marked `missing` (find-missing) or `ended`, as the row itself does (SR-8.2).
- **N10 Foreground visibility, and its residuals.** A running foreground subagent shows as soon as its start claims a claimable launch (SR-4.5). A claim only confirms, so each residual below but the last is of visibility only: no field is ever taken from a claim (N11). Documented residuals:
  - A subagent whose start claims nothing shows only when its launch result arrives, which for a foreground subagent is when it finishes. Its start claims nothing when no claimable launch of its type is open as the start is applied: for example its launch request opened none (it carries `tool_input.name`, or no `tool_input.subagent_type`), or another start claimed it first. A start for an id that already has an entry never claims (SR-4.5), so an entry its first start did not confirm stays hidden across its restarts (F3) until its launch result or a listing confirms it.
  - A start can claim a claimable launch that is not its own launch's: a stale one ([D] a failed call's; on every baseline a denied or blocked call's, each open until a main-agent Stop past the grace; or a repeated launch request's; SR-4.5), or, when a named or typeless launch's start comes first, another launch's of its type, whose own subagent then shows only at its launch result. A subagent confirmed this way is still a subagent, so its confirmation is correct.
  - The one wrong confirmation: an in-process teammate whose name equals the `subagent_type` of an open claimable launch, and whose first start is applied while that launch is open, shows as one record (never one per message), with no field from the claim. This narrows the PRD's "teammates produce no subagent records".
  - Not a residual of visibility, but documented with them, and unprobed (the probe saw no teammate launch a subagent): a subagent launched by an in-process teammate has the teammate's id as its `parent_id`, with `parent_type` `subagent` (SR-6.3), and no record of that parent exists, since teammates are not tracked (SR-4.3).
- **N11 A running foreground subagent's fields.** While a foreground subagent runs, its record has its `subagent_type`, from its start's `agent_type` (SR-6.3), and its `description`, `model`, `parent_type`, `parent_id`, `tool_use_id` and `run_mode` are null: no payload of its own gives them before its `completed` launch result (Q1, F11, F13), and a claim gives none (SR-4.5). The launch result sets them all when the subagent finishes. Nothing shown is ever another launch's value (the PRD's unknown rule). A background subagent whose launch result was lost looks the same until a listing fills its `run_mode` (SR-7.4, SR-7.6). The PRD acceptance criterion "a running record ... with type, description, model, parent, instance id, session id and start time as fields" is narrowed to this: every key is present while the subagent runs, and these values stay null until a payload supplies them (SR-6.4).
- **N12 "The same record whatever the order".** The PRD's "the record ends up the same whatever the order" and "delivered twice ... produce the same record" mean the same fields, confirmation and state, with one exception, `session_id`: it is the session id of the event that created the entry (SR-6.3), and a subagent's events carry different session ids only across a change of the agent's session, such as `/clear` (F4), so only then can it depend on the order. Receipt times can still differ by the gap between racing hooks, a few milliseconds (0.07 to 2 ms in the probe): a background launch's `started_at` is the receipt time of its start or of its `async_launched` result, whichever is applied first (SR-7.1, SR-7.3). `first_started_at` and `stopped_at` do not depend on the order (SR-6.5, SR-7.7). A duplicate SubagentStart that arrives after the entry stopped cannot be told from a restart (F3), so it reopens the entry (SR-7.1), and a SubagentStop with `stop_hook_active` true delivered twice moves `stopped_at` to the later delivery (SR-7.2). When another stop hook blocks a SubagentStop, the record reads `stopped` while the subagent keeps running, until its real stop (`stop_hook_active` true) updates `stopped_at` (SR-7.2).
- **N13 A missed launch has no description.** The PRD's "It holds what the snapshot provides" is narrowed: a listing's `description` is never stored. It is Claude Code's own label for the task, not the description the launching call gave (the metadata the PRD keeps), and it can be prompt text (the teammate entry in `s9.jsonl` holds the start of its prompt) or `(resumed)` (`s10.jsonl`). A record a listing creates holds the listed id, the listing's `agent_type` as its type, `background` as its run mode and the Stop's `session_id`; its `description` stays null until its launch result supplies one. b.2qh agreed this ("Contract agreement"; SR-6.3, SR-7.4).

## SR-2: Hook registration

### SR-2.1: Settings
- The settings every launch synthesizes (spawn, resume, reuse; `internal/spawn` `synthesizeSettings` over `hookEvents`) register SubagentStart and SubagentStop in addition to the baseline's events: [D] eight, so ten; [R+S] nine (with PostToolUseFailure), so eleven.
- Each new entry is in exec form like the others: `command` is the resolved agent-director binary path, verbatim; `args` is exactly `["hook"]`; no `matcher`; no inner `timeout`.
- Nothing else in the settings changes: every other entry (PreToolUse keeps its `"*"` matcher), the relay and SessionStart timeouts, [R+S] the PermissionRequest `--timeout` argument, the permissions block and the `inject_help_hook` entry are as on the baseline.

### SR-2.2: Classification
- `internal/hook` `ClassifyEvent` knows SubagentStart and SubagentStop: both are soft refreshes, and neither is an unknown event (no "unknown event" log line).
- Neither is a SessionStart or SessionEnd, so neither is ever ignored as `subagent_event`.
- PreToolUse, PostToolUse, [R+S] PostToolUseFailure and Stop keep their classification.
- The classifier is not loosened: it parses the same payload fields as on the baseline, each as a string, and a payload in which one of them has another JSON type still fails classification and is handled as today (SR-5.1).

### SR-2.3: Claude Code version
- The minimum stays 2.1.280 (F10, F11). README.md and docs/install.md are unchanged on this point.

## SR-3: Gate and store transactions
The rules here are the ones the TLA+ model checked, with the refinements SR-14.1 shows need no new run. A change to any of them needs a new model check before it lands.

### SR-3.1: Every entry write from a hook is gated
- Every statement that creates, changes or deletes an entry or a claimable launch for a hook event (SR-4.5, SR-7) carries the existing gate (`hookGateSQL` with `hookGateArgs`, `internal/store`) in its own WHERE, with four row conditions in the same statement: the row is live; the row's current launch is tracked (SR-9); the row's `launch_token` is not null; and the row's current `launch_token`, read in that statement, decides the launch: an entry or a claimable launch is created only in it, an entry is moved only into it, and a stop, a snapshot close or a claim acts only on what belongs to it. The gate and the row conditions are never checked in a separate read before the write; a read of the entry that decides a transition happens inside the write's transaction, after its write lock is taken.
- So a hook from any process but the row's recorded pane process (a nested `claude`, a teammate pane, a leftover, a stray), and every hook while the row records no pane, writes no entry and no claimable launch.
- Such a hook is reported exactly as today: one `ad.hook.ignored` (`pid_mismatch` or `no_pane_recorded`) from its row write, and none when no row has the id. An entry statement that finds the gate no longer holding writes nothing and adds no trail record.

### SR-3.2: SubagentStart and SubagentStop
- The row write is today's gated soft refresh of an ordinary hook: the state stays; no session id or transcript path is recorded (the payload carries `agent_id`); `last_seen_at` is bumped; the liveness markers are cleared; the pane start time is recorded when NULL; `row_version` advances by one; one `ad.spawn.state_transition` with `soft_refresh` true is emitted. [R+S] Unlike the soft refresh of every other hook there, it leaves `idle_since` as it is, so find-missing's repair of a stale `check_permission` row and the relay behave exactly as today (SR-13.1). [S] It writes no settle column.
- The row write and the hook's entry writes (a claim included) run in one `BEGIN IMMEDIATE` transaction on the store's one connection (the "write lock before the read" rule of docs/architecture.md): both commit, or neither does. The entry writes run only when the row write applied.
- Trail records are emitted only after the transaction ends: the row write's `ad.spawn.state_transition` only after a commit, and `ad.hook.fired` as the hook exits.
- `ad.hook.fired`'s `upsert_outcome` is the row write's: `updated` when the transaction committed; `no_change` when the gate refused the row write (with its one `ad.hook.ignored`) or no row has the id; `error` when the transaction rolled back for any reason, an entry write's failure included, as for any failed row write today. The failure is logged in one line with no content, and the hook exits 0.
- A SubagentStart or SubagentStop whose `agent_id` is absent, null or empty (SR-5.1) writes no entry, claims nothing and applies no listing, and is otherwise treated as today's hooks are: its row write is this soft refresh under today's session rule for a hook without `agent_id` (`internal/hook` `Handle`), so it records the session id and transcript path on a row that records none. [R+S] It too leaves `idle_since` as it is.
- Each applied SubagentStart and SubagentStop advances `row_version` by one, as every applied hook write does, so each run of a subagent adds two advances. This churn is accepted: a snapshot-guarded write that one of them overtakes is refused as changed and handled as it is today when any other hook overtakes it (SessionStart's identity write re-reads and retries once; find-missing's guarded writes and expire's delete leave the row to their next run).

### SR-3.3: The launch request, the launch result, [R+S] PostToolUseFailure(Agent), and the main-agent Stop
- The row write is exactly today's: [R+S] with the request proofs, the tool-ran close and the working hold; [S] with the settle columns.
- The entry and claimable-launch writes run after it, in their own `BEGIN IMMEDIATE` transaction, only when the row write applied (a held working transition counts as applied), whether or not the state moved. SR-12.2 says when a Stop skips that transaction.
- That transaction emits no trail record. If it fails, it rolls back whole, the failure is logged in one line with no content, and `upsert_outcome` stays the row write's.
- The model checked this split: its `SubHook` is one gated step, a soft refresh with the entry write, and a hook's own row write is a separate step (`HookAct`), which only adds interleavings, so the safety shown for the split holds for both transaction forms (tla/README.md).
- Only the hooks of SR-3.2 and of this section write entries or claimable launches; of these, a hook for a tool other than `Agent` and a Stop carrying `agent_id` write neither.

### SR-3.4: Terminal rows
- No hook creates, changes or reopens an entry, or opens a claimable launch, while the row is `ended` or `missing`, its pane process's hooks included: a SubagentStop can follow SessionEnd while the process still runs (control `sx_C_terminal`).

### SR-3.5: Clocks and transactions
- The store reads no clock for an entry write or a claimable-launch write made for a hook event, or for the closes of resume's move and reuse's reset: each instant it writes there is passed in by the caller (SR-6.2), so tests inject it. The closes of the terminal SessionEnd write and of find-missing's mark take their instant from the store's own clock, read once inside that write's transaction at millisecond precision, as each of those writes sets `ended_at` from the store's clock today. No existing signature changes for it (SR-8.1), and tests assert that instant within the write's window (SR-15.2).
- [D] `ApplyHookTransitionResult` is not transactional. It stays so for every other hook, except its ended transition, which becomes a transaction carrying the close (SR-8.1).
- The SubagentStart and SubagentStop write of SR-3.2 is a store method of its own, on every baseline: unlike `ApplyHookTransitionResult`'s soft refresh, which runs outside any transaction and [R+S] clears `idle_since`, it shares one `BEGIN IMMEDIATE` transaction with its entry writes and [R+S] leaves `idle_since` alone (SR-3.2).

## SR-4: Entry identity and confirmation

### SR-4.1: Key and launches
- An entry is identified by (instance id, subagent id) across all the row's launches and lives. The pair is the stable id of a record. The session id and the launch token are fields, not part of the key.
- An entry belongs to the launch in its `launch_token`: the row's launch at the entry's latest start, launch result or listing. Each of those writes moves an entry of an earlier launch into the current launch (SR-7). A stop and a snapshot close act only on an entry of the current launch.
- An entry of an earlier launch is never running: the write that began the current launch closed it (SR-8.1), and only a start reopens it, moving it.
- Records of earlier launches and lives stay, closed, until retention or row deletion removes them (SR-10.3).

### SR-4.2: Observations and records
- Only a SubagentStart creates an observation (SR-7.1). Every other creation (SR-7.3, SR-7.4) creates a record.
- For Claude Code, an observation becomes a record when a payload confirms its id as a subagent: its first start's claim of a claimable launch (SR-4.5); a launch result whose `tool_response.agentId` is the id, whatever its status; or a listing of the id in a main-agent Stop's or a SubagentStop's `background_tasks`. A record never becomes an observation again.
- An observation keeps its times, state and fields, and the record it becomes has them: confirmation changes no time.
- No verb returns an observation. Observations count against the cap, are closed as records are (SR-8) and are deleted with the row; the cap deletes a closed observation before any closed record (SR-10.3).

### SR-4.3: Teammates
- In-process teammates are confirmed by no payload field, so they produce no record (N10's residual aside). Their per-message SubagentStarts reuse one id (F5), so a teammate holds one entry, never one per message, and only its first start could claim.
- A teammate spawn's PreToolUse(Agent) carries `tool_input.name`, so it opens no claimable launch (SR-4.5).
- A `background_tasks` entry whose `type` is not `subagent` is ignored: no field but its `type` is read.
- A PostToolUse(Agent) with no `tool_response.agentId` (a teammate's `teammate_spawned`) writes no entry.

### SR-4.4: Internal agents and stray events
- A SubagentStop for an id with no entry of the current launch: its stop creates and changes nothing (F8); its listing still applies (SR-7.6).
- A tool hook carrying `agent_id` writes no entry and no claimable launch unless it is a PreToolUse, PostToolUse or [R+S] PostToolUseFailure whose `tool_name` is `Agent`; its row write is today's.
- A SubagentStart or SubagentStop with no `agent_id` writes no entry and claims nothing (SR-3.2).

### SR-4.5: Claimable launches (Claude Code)
- A PreToolUse whose `tool_name` is `Agent`, with `tool_use_id` and `tool_input.subagent_type` supplied and `tool_input.name` not supplied (SR-5.1), opens a claimable launch in the current launch, holding the call's `tool_use_id`, its `subagent_type` and the receipt time, and nothing else. Any other PreToolUse(Agent) opens none: one whose `tool_use_id` or `tool_input.subagent_type` is not supplied, or whose `tool_input.name` is.
- A launch request whose `tool_use_id` already has an open claimable launch, or is already the `tool_use_id` of an entry of the current launch, changes nothing, so a repeated request opens no second claimable launch. A claim records nothing, so a repeat delivered after its start's claim and before its launch result is not recognised: it opens a stale claimable launch, which that call's launch result closes unless a start claims it first (N10).
- A SubagentStart that creates an entry (no entry had its id) claims the oldest open claimable launch of the current launch whose `subagent_type` equals the start's `agent_type` (oldest by receipt time, then by creation order). The new entry is confirmed at once, and the claimable launch closes. A claimable launch is claimed by at most one start, and a start claims at most one. A start on an existing entry, or one whose `agent_type` is not supplied, never claims.
- A claim only confirms the entry: it fills no field. The claimed launch need not be the start's own (N10), so none of its values is copied: the entry's `subagent_type` is its start's `agent_type`, and its `description`, `tool_use_id`, `parent_type`, `parent_id`, `model` and `run_mode` stay null until its own launch result, or a listing for `run_mode` (N11).
- A claimable launch closes, and is deleted, at the first of: its claim; a launch result with its `tool_use_id`, whatever its status; [R+S] a PostToolUseFailure(Agent) with its `tool_use_id`; a main-agent Stop whose receipt time is more than 2 s after the claimable launch's (the grace of SR-7.5), whether or not that Stop carries a snapshot; a write of SR-8.1. A claimable launch that no launch result and no failure closes waits for the next main-agent Stop past the grace: [D] a failed call's, since PostToolUseFailure is not registered there; and, on every baseline, a denied or blocked call's.
- Claimable launches are internal: no verb returns them and no output counts them. Their writes are gated as entry writes are (SR-3.1), a start claims only a claimable launch of the current launch, and a row holds at most 300 (SR-10.3).
- N10 states the residuals of this rule; docs/usage.md documents them, and docs/hooks.md links to it (SR-16).

## SR-5: Payload fields read; no content

### SR-5.1: The only fields read
- SubagentStart: `session_id`, `agent_id`, `agent_type`.
- SubagentStop: `agent_id`, `stop_hook_active`, and its `background_tasks` as below.
- PreToolUse whose `tool_name` is exactly `Agent`: `tool_use_id`, `tool_input.subagent_type`, and whether `tool_input.name` is supplied (its value is never kept). Nothing else of it is read for subagent records: a claimable launch holds only these and the receipt time, and a claim copies nothing (SR-4.5).
- PostToolUse whose `tool_name` is exactly `Agent` (as 2.1.280 names the tool): `session_id`, `agent_id` (absent on a main-agent launch), `tool_use_id`, `tool_input.description`, `tool_input.subagent_type`, `tool_response.agentId`, `tool_response.status`, `tool_response.resolvedModel`, and, from a `completed` result only, `tool_response.agentType` (the type, not content; SR-6.3).
- [R+S] PostToolUseFailure whose `tool_name` is exactly `Agent`: `tool_use_id`.
- Stop: `session_id`, `agent_id` (a Stop carrying one is ignored here: SR-7.4), and its `background_tasks` as below.
- `background_tasks`, a Stop's or a SubagentStop's: each entry's `type`; for an entry whose `type` is `subagent`, its `status` and `id`; for an entry that lists a subagent, also its `agent_type` (used only when the listing creates the entry, SR-6.3). No entry's `description` is read (SR-5.2, N13).
- *Supplied.* A field is supplied when it is present, not null, of the JSON type it is read as and, for a string, not empty. Every field read is a string except `stop_hook_active`, a boolean; `background_tasks`, an array (an entry of it that is not an object lists no subagent); and `tool_input` and `tool_response`, objects (when one is not an object, no field inside it is supplied). Every rule of this SRD that depends on a payload field uses this meaning: an event that carries a field, or has it, supplies it; one with no such field, or without it, does not.
- A field only this feature reads that is not supplied, a value of another JSON type included, is treated as absent, and that never fails the hook. These are `session_id`, `agent_type`, `stop_hook_active`, `background_tasks` and the fields read from its entries, every `tool_input.*` and `tool_response.*` field, and [D] `tool_use_id`.
- A field the classifier already parses keeps today's rule; the classifier is not loosened (SR-2.2). These are the fields of `internal/hook` `ClassifyEvent`'s payload: `hook_event_name`, `event_name`, `tool_name`, `reason`, `matcher`, `endReason`, `transcript_path`, `agent_id`, `notification_type` and [R+S] `tool_use_id`. Absent, null or empty is not supplied. A value of another JSON type fails the payload's classification, as today: the hook logs one line, exits 0, and writes no row, no entry and no claimable launch.
- A SubagentStart or SubagentStop with no `agent_id` writes no entry (SR-3.2), and a launch request with no `tool_use_id` opens no claimable launch (SR-4.5). A `background_tasks` that is absent or not an array is no snapshot and closes no entry. A `background_tasks` entry that lists no subagent is ignored: it creates, fills and confirms nothing, and does not keep its id from a snapshot's close. None of these fails the hook.

### SR-5.2: Never read, kept or written
- No other field is read into any value the hook keeps. In particular, these never reach the store, the trail or the hook's log: `prompt`, `tool_input.prompt`, `tool_response.prompt`, `tool_response.content`, `last_assistant_message`, `agent_transcript_path`, `tool_response.outputFile`, `tool_response.agent_id`, the value of `tool_input.name`, [R+S] PostToolUseFailure's `error`, every field but `type` of a `background_tasks` entry whose `type` is not `subagent` (a teammate's `description` holds its prompt), the `description` of every `background_tasks` entry (Claude Code's own label, N13), `session_crons`, and any message text (SendMessage's input and response included).
- A `completed` result's token counts and tool activity (`usage`, `totalTokens`, `totalToolUseCount`, `totalDurationMs`, `toolStats`) are out of scope (a PRD non-goal) and never read.
- Only the fields of SR-6.1 are stored, with the internal columns of SR-10.1 and SR-10.5. The description is metadata and is kept: for Claude Code it is only the Agent tool call's `description` parameter, its short description, never prompt text (SR-6.3).
- Scope (N8): a relayed PermissionRequest's `tool_input`, which the relay stores today, is unchanged.

### SR-5.3: Stored strings are bounded
- Every string this feature takes from a payload is cut to at most 1 KiB (1024 bytes) before it is compared, matched or stored: a subagent id (`agent_id`, `tool_response.agentId`, a listing's `id`), `session_id`, a type (`agent_type`, `tool_input.subagent_type`, `tool_response.agentType`), the description (`tool_input.description`), the model (`tool_response.resolvedModel`) and `tool_use_id`, in entries and claimable launches alike.
- A longer value keeps its longest prefix of whole UTF-8 characters within 1024 bytes, so no stored string ends in part of a character, and a value always matches the entry or claimable launch stored from it. A value of 1024 bytes or less is unchanged.
- The instance id comes from the row, not a payload, and is never cut.

## SR-6: Record fields and their sources

### SR-6.1: Fields
Every record carries every one of these keys on every surface. An unknown value is an explicit null, never an omitted key.

| Field | Type | Meaning |
|---|---|---|
| `subagent_id` | string | the agent's id for the subagent (Claude Code's `agent_id`); never null |
| `instance_id` | string | the agent-director id of the agent the record belongs to; never null |
| `session_id` | string or null | the session id of the event that created the entry |
| `subagent_type` | string or null | the subagent's type |
| `description` | string or null | the short description the launching call gave it; never prompt text |
| `model` | string or null | the model the launch resolved |
| `parent_type` | `agent`, `subagent` or null | who launched it; null is unknown |
| `parent_id` | string or null | the instance id when `parent_type` is `agent`; the launching subagent's id when `subagent`; null when unknown |
| `tool_use_id` | string or null | the launching tool call's id |
| `run_mode` | `background`, `foreground` or null | how it ran; null is unknown |
| `first_started_at` | timestamp or null | the earliest start received |
| `started_at` | timestamp or null | the start that last made it running |
| `stopped_at` | timestamp or null | the stop that last made it stopped |
| `lost_at` | timestamp or null | when it was judged lost |
| `state` | `running`, `stopped` or `lost` | never null |
| `close_reason` | `stop_event`, `absent_from_snapshot`, `agent_gone` or null | null exactly while `running` |

- For Claude Code, a start in these meanings is a SubagentStart or an `async_launched` launch result, and a stop is a SubagentStop or a `completed` launch result. A SubagentStop's receipt time wins over a `completed` result's, and a SubagentStop with `stop_hook_active` true on a `stopped` entry updates `stopped_at`, since the stop before it was blocked by another stop hook (SR-6.5, SR-7.2).
- `stop_event`: the agent reported the subagent finished (for Claude Code, its SubagentStop or its launch's `completed` result). `absent_from_snapshot`: a snapshot of the agent's running background tasks, which covers it, did not list it. `agent_gone`: its agent's row ended, went missing, or began a new launch.
- (`instance_id`, `subagent_id`) is unique: it is the stable id of a record.
- Every string field taken from a payload holds at most 1 KiB of UTF-8 (SR-5.3).
- The value sets of `state`, `close_reason`, `parent_type` and `run_mode` are fixed and documented; adding a value later is an additive change.

### SR-6.2: Times
- Every time is a UTC instant with millisecond precision, stored as integer milliseconds since the epoch.
- A time is shown as an RFC 3339 string in UTC ending in `Z`, encoded as AD's existing millisecond field `launch_started_at` (`get`, `list`, `status`) is: Go's `time.Time` JSON form (RFC3339Nano), with the fraction to the millisecond and its trailing zeros dropped (`2026-10-11T15:17:03.12Z`), and no fraction on a whole second (`2026-10-11T15:17:03Z`). CLI JSON and the MCP result carry that string; the Go library returns a UTC `time.Time` whose JSON is that string; the TypeScript client returns the same string. An unknown time is null (SR-6.1).
- Times are agent-director's receipt times; no time is taken from a payload. A hook event's receipt time is the instant its hook process started, read before the payload: [R+S] `HandleConfig.Start`, read first thing in the hook verb; [D] the same instant is added there.
- An `agent_gone` close's `lost_at` is the instant of the write that closed it (SR-8.1). For the terminal SessionEnd write and find-missing's mark, it is the store's own clock, read once inside that write's transaction at millisecond precision, as each of those writes sets `ended_at` from the store's clock; for resume's move and reuse's reset, it is the new launch's `launch_started_at`.

### SR-6.3: Sources and precedence
- `subagent_type`: SubagentStart `agent_type`, over the launch result's type, over the `agent_type` of the listing that created the entry. The launch result's type is its `tool_input.subagent_type` or, when that is not supplied, a `completed` result's `tool_response.agentType`: the type the launch resolved, not content.
- `description`: only the launch result's `tool_input.description`, the Agent tool call's `description` parameter (its short description, never prompt text). No claim and no listing is a source (SR-4.5, N13).
- `model`: the launch result's `tool_response.resolvedModel` only.
- `parent_type` and `parent_id`: the launch result's only. With an `agent_id`, `subagent` and that id, kept even when no entry has that id; without one, `agent` and the instance id.
- `tool_use_id`: the launch result's only.
- `run_mode`: the launch result's `tool_response.status` (`async_launched` is `background`, `completed` is `foreground`, any other status supplies nothing), over any listing (`background`: a listed subagent is a background task, F12).
- `session_id`: the `session_id` of the event that created the entry; never changed afterwards, a move to another launch included.
- A claim is a source of nothing: it only confirms (SR-4.5).
- A listing's `agent_type` is used only when that listing creates the entry (SR-7.4): a listing never sets or changes the type of an entry it did not create. No listing sets or changes a description.
- A value from a higher-precedence source replaces one from a lower; a lower one only fills an unknown value; a source never replaces a value it set itself, so a second value from the same source changes nothing, and a field with one source keeps its first value. The entry records which source set each field that has more than one (SR-10.1), so the result does not depend on arrival order. Times follow SR-6.5 and SR-7, not these rules.
- Every event applies its fields by these rules, whatever it does to the state.

### SR-6.4: Unknown, never guessed
- A field no event supplied is null; nothing is inferred. A consumer places a record with a null parent under its `instance_id`.
- For Claude Code: a record created from a snapshot has no start times until a start arrives, and no description until its launch result (N13); a model is never taken from the agent or from anywhere but the launch result; `parent_type` is `agent` only when a main-agent launch result said so, and otherwise the parent is null until a launch result, never the agent; a claim supplies no value, so a running record never shows another launch's value, nor one from its own launch request (N11); a `completed` result's `agentType` is the type the launch resolved, supplied by the payload; and a `run_mode` of `background` from a listing is supplied by the hook, not inferred, since the list holds background tasks only (F12).

### SR-6.5: Invariants
- `running`: `close_reason` and `lost_at` are null.
- `stopped`: `close_reason` is `stop_event`, `stopped_at` is set, `lost_at` is null.
- `lost`: `close_reason` is `absent_from_snapshot` or `agent_gone`, and `lost_at` is set. `absent_from_snapshot` appears only on an entry whose `run_mode` is `background`.
- `stopped_at`, once set, is kept across restarts. It holds the receipt time of the stop that last made the entry `stopped`, with two exceptions for Claude Code: a SubagentStop's receipt time wins over a `completed` launch result's, whichever of the two came first, and a SubagentStop with `stop_hook_active` true on a `stopped` entry replaces it (SR-7.2).
- `first_started_at` is the earliest receipt time of the starts applied to the entry (for Claude Code, SubagentStarts and `async_launched` launch results): once set, it only moves to an earlier one. `started_at` is never before it. Once a start or an `async_launched` result has been applied to an entry, both are set.

## SR-7: Transitions
Each applies on a live and tracked row, from a hook that passed the gate, inside the transaction of SR-3, to the entry with the event's subagent id, whichever launch it belongs to, unless the rule says "of the current launch". A write that changes an entry sets its `activity_at` to the receipt time.

### SR-7.1: Start (SubagentStart)
- No entry: an observation of the current launch, `running`, with `first_started_at`, `started_at` and `opened_at` the receipt time; confirmed at once when the start claims a claimable launch (SR-4.5), which fills no field.
- `running` (always of the current launch): the state is unchanged; a null `started_at` is set to the receipt time (an entry a listing created first), and a set one is unchanged (a repeat, or a start applied after its racing `async_launched` result, N12); `first_started_at` takes the receipt time when it is null or holds a later one.
- `stopped` or `lost`, of any launch: `running` again, moved to the current launch; `started_at` and `opened_at` become the receipt time; `close_reason` and `lost_at` are cleared; `stopped_at` is kept with its source; `first_started_at` takes the receipt time when it is null or holds a later one (F3).

### SR-7.2: Stop (SubagentStop)
- An entry of the current launch, `running` or `lost`: `stopped`, with `stopped_at` the receipt time (its source a stop) and `close_reason` `stop_event`; `lost_at` is cleared. A real stop overrides an inferred `lost`.
- An entry of the current launch, `stopped`: the state is unchanged. `stopped_at` becomes the receipt time (its source a stop) when its value came from a `completed` launch result, since a SubagentStop's time wins over a result's, or when this stop carries `stop_hook_active` true, since the stop before it was blocked by another stop hook and this one is the real stop. Otherwise nothing changes.
- No entry, or an entry of an earlier launch: the stop changes nothing (SR-4.4).
- In every case, its `background_tasks` then applies as SR-7.6 says.

### SR-7.3: Launch result (PostToolUse(Agent))
- It closes the open claimable launch with its `tool_use_id`, if there is one (SR-4.5), whatever else it does.
- No `tool_response.agentId`: no entry is written.
- An entry exists, of any launch: its fields are applied, and it is confirmed and moves to the current launch. Then, by `tool_response.status`:
  - `async_launched`: a null `started_at` is set to the receipt time, and a set one is unchanged; `first_started_at` takes the receipt time when it is null or holds a later one; the state is unchanged.
  - `completed`: `running` or `lost` becomes `stopped`, with `stopped_at` the receipt time (its source the launch result) and `close_reason` `stop_event`, and `lost_at` cleared; `stopped` is unchanged, its `stopped_at` included. Start times are unchanged.
  - any other status: state and times are unchanged.
- No entry, `async_launched`: a record of the current launch, `running`, with `first_started_at`, `started_at` and `opened_at` the receipt time.
- No entry, `completed`: a record of the current launch, `stopped`, with `stopped_at` (its source the launch result) and `opened_at` the receipt time, `close_reason` `stop_event`, and null start times.
- No entry, any other status: no entry.
- [R+S] A PostToolUseFailure(Agent) closes the claimable launch with its `tool_use_id` and does nothing else. It is never a source of fields: a launch that fails before a subagent exists writes no entry (Q5).

### SR-7.4: Snapshot (a main-agent Stop): create, fill, confirm
- A main-agent Stop's `background_tasks` array is a snapshot. A Stop carrying `agent_id` is ignored here entirely: it creates, fills, confirms and closes no entry, and closes no claimable launch.
- A listed id with no entry: a record of the current launch, `running`, with `run_mode` `background`, `subagent_type` the listing's `agent_type`, `session_id` the Stop's, every other field null (`description` and both start times included, N13), and `opened_at` the Stop's receipt time.
- A listed id with an entry, of any launch: the entry is confirmed and moves to the current launch, and a null `run_mode` becomes `background`; the listing's `agent_type` is not used (SR-6.3). Its state and times never change: a snapshot never reopens a `stopped` or `lost` entry (PRD), because a real restart sends SubagentStart, and a running subagent closed wrongly is corrected by its own SubagentStop (`lost` to `stopped`, SR-7.2).
- A `background_tasks` entry that lists no subagent does nothing (SR-5.1).

### SR-7.5: Snapshot: close
- In the same transaction, after SR-7.4: every `running` entry of the current launch whose `run_mode` is `background`, whose id the snapshot does not list, and whose `opened_at` is more than 2 s (a fixed constant) before the Stop's receipt time becomes `lost`, with `close_reason` `absent_from_snapshot` and `lost_at` the Stop's receipt time.
- An entry whose `run_mode` is `foreground` or null is never closed by a snapshot: its stop (SR-7.2, SR-7.3) or liveness (SR-8) closes it (F12; N3).
- Background entries are covered process-wide: they are not filtered by session id or nesting (N3).
- An entry opened less than 2 s before the Stop hook started, or after it, is never closed by that snapshot. An entry of another launch is never touched.
- The same Stop closes claimable launches as SR-4.5 says.

### SR-7.6: SubagentStop's `background_tasks`
- Each listed id with an entry, of any launch: the entry is confirmed and moves to the current launch, and a null `run_mode` becomes `background`; the listing's `agent_type` is not used (SR-6.3). It never creates, closes or reopens an entry, and never changes state or times.

### SR-7.7: Repeats and order
- An event applied again right after itself, with its own receipt time, changes no field, state or time.
- In every order of N6 an entry ends with the same fields, confirmation and state (N12), `session_id` excepted: it is the session id of the event that created the entry (SR-6.3), so it can depend on the order only when a change of the agent's session, such as `/clear`, falls between the entry's events (F4). Its times are the receipt times the rules assign, and two of them do not depend on the order: `first_started_at` is the earliest receipt time of the starts and `async_launched` results applied, and no order leaves it null once one of them has been applied (a listing that created the entry before its start, as in `s4.jsonl`, included); `stopped_at` is the receipt time of the SubagentStop that stopped the entry, whether it came before or after a `completed` result, and the result's when no SubagentStop came. `started_at` is the receipt time of whichever of a start and its racing `async_launched` result was applied first (N12).

### SR-7.8: Launch request (PreToolUse(Agent))
- It opens a claimable launch as SR-4.5 says, and writes no entry.

## SR-8: Reconcile from liveness

### SR-8.1: Writes that close
- Each of these writes turns every `running` entry of the row (records and observations) to `lost`, with `close_reason` `agent_gone`, and `lost_at` and `activity_at` that write's instant, and deletes every claimable launch of the row. The close is in the same transaction as the write and applies only when the write applied; both commit or neither. Each write, with its instant:
  - the terminal SessionEnd write (`ended`): the store's own clock, read once inside that write's transaction, at millisecond precision (SR-6.2);
  - find-missing's mark (`MarkMissingIfSameLife`, `missing`): the store's own clock, read once inside the mark's transaction, at millisecond precision;
  - resume's move to pending (`MoveToPending`): the new launch's `launch_started_at`, which the move writes;
  - reuse's reset (`ResetForReuse`): the new launch's `launch_started_at`, which the reset writes.
- No signature changes. The ended hook write and find-missing's mark take no instant today: each sets `ended_at` from the store's clock inside its own write. Their close reads its instant from the store's own clock too, inside the write's transaction and at millisecond precision, so both keep their signatures: `MarkMissingIfSameLife` keeps its signature on the store and in the exported `api.FindMissingStore`, and `markMissingSameLife` and the sweep are unchanged; the ended hook write (`ApplyHookTransitionResult`; [R+S] the `applyEndedTransition` it calls) and the `internal/hook` interface the handler calls it through (`outcomeTransitioner`) keep theirs. `MoveToPending` (its `launchStartedAtMillis`) and `ResetForReuse` (its fresh row's `LaunchStartedAtMillis`) already take the new launch's `launch_started_at`. The columns these writes set today, `ended_at` among them, keep their sources.
- [D] The ended hook write and `MoveToPending` are single statements: each becomes a `BEGIN IMMEDIATE` transaction carrying the close. [R+S] Both already run in such a transaction (with the close of the row's permission requests); the entry close joins it. `MarkMissingIfSameLife` and `ResetForReuse` are such transactions on every baseline.
- The failed-launch restores (`RestoreAfterFailedResume`, `RestoreAfterFailedReuse`) close nothing and stay single statements. They apply only while the row is still pending at the version the move or reset produced, so no hook has written an entry or a claimable launch since (the row records no pane), and the move or reset already closed every running entry. They write the tracking flag back (SR-9).
- The held-launch end (`EndHeldLaunch`) needs no close: that launch never records a pane, so no hook can write an entry for it.

### SR-8.2: What does not close
- `kill` writes no state, and the SessionEnd a killed agent sends (reason `other`, F9) is not terminal (N9). A killed agent's entries turn `lost` when its row is marked `missing` or `ended`, as the row itself does.
- A find-missing run that leaves the row unverified or notes it `unreported` changes no entry; neither does any note, note clear or adoption write.
- A SessionEnd that is not terminal (`clear`, `compact`, `other` and the rest) changes no entry.

### SR-8.3: A row that comes back
- An `ended` or `missing` row that a hook from its own pane process moves back to a live state accepts entry writes again: the non-terminal row write carries the gate but no state guard. The entries closed when the row ended or went missing stay closed until a real start reopens one (SR-7.1); a stop or a `completed` launch result can turn a `lost` one `stopped` (SR-7.2, SR-7.3), and a listing reopens none (SR-7.4). `tla/README.md` argues that this needs no new model run (SR-14.1).

### SR-8.4: Invariant
- No entry is `running` on an `ended` or `missing` row, and no entry whose `launch_token` is not the row's current one is `running` (`SubNoStaleRunning`).

## SR-9: Tracking-covered field
- `spawns` gains `subagent_tracking` (integer, not null, default 0): 1 when the settings the row's current launch was given register the agent's subagent start and stop events.
- Each launch write (`InsertPending`, `MoveToPending`, `ResetForReuse`) sets it for the launch it begins. On this build each stores 1 and takes no new parameter: the settings every launch synthesizes always register SubagentStart and SubagentStop (`synthesizeSettings`, SR-2.1). No exported interface changes for it: `api.ResumeStore` keeps `MoveToPending` and `RestoreAfterFailedResume` as they are (SR-13.1).
- A failed launch's restore writes back the value the row had before that launch: the pre-reuse life (`RawLife`) and resume's `ResumePrior` carry it as a field, so no restore takes a new parameter either.
- A row from before the upgrade keeps 0 until its next launch. No hook, sweep or other verb writes it.
- Entry and claimable-launch writes require it to be 1 (SR-3.1).
- It is shown only as `list_subagents`' `tracked`; `get` and `list` do not show it.

## SR-10: Storage, schema and retention

### SR-10.1: The `subagents` table
- One row per entry, with: `created_seq` (the table's `INTEGER PRIMARY KEY AUTOINCREMENT`, an alias of its rowid: it grows with each insert and is never reused, and so orders the table's entries by creation; never changed); `instance_id` (not null; a foreign key to the `spawns` row, `ON DELETE CASCADE`); `subagent_id` (not null); `launch_token` (not null: the launch the entry belongs to, SR-4.1); `confirmed` (integer 0 or 1, not null); the other SR-6.1 fields under the same names, with times as integer milliseconds and `state` not null; `opened_at` (integer milliseconds, not null: the latest time the entry became `running`, or its creation time if it never was); `activity_at` (integer milliseconds, not null: the instant of the latest write that changed it, an event's receipt time or a closing write's instant); and, for each value with more than one source, which source set it, null while the value is unknown: `subagent_type_source` (`start`, `details` or `snapshot`), `run_mode_source` (`details` or `snapshot`) and `stopped_at_source` (`stop` or `details`). `description`, `model`, `tool_use_id`, `parent_type` and `parent_id` have one source each, the launch result (SR-6.3), so they have no source column.
- Unique on (`instance_id`, `subagent_id`), with an index that serves the per-row read, the per-launch transitions and the cap.
- `internal/store` is the only package that reads or writes it.

### SR-10.2: The schema hop
- One hop, at the next free version when the work is built: the version after the newest one merged then ([D] alone: v7; with R merged: v8; with S merged: v9; one more for each other hop merged first). It is never folded into another unreleased hop, and the number is checked again at merge.
- `schemaVersion`, `schemaDDL` and the `migrationSteps` registry move together (the two-places rule): a fresh store is created at the new version with both tables and the column, and a migrated store has the identical shape.
- The hop creates both tables and their indexes (`IF NOT EXISTS`) and adds `spawns.subagent_tracking` behind a `pragma_table_info` probe. It stamps the version last, is idempotent on re-entry, rolls back whole on any failure, and has no backfill: every existing row reads `subagent_tracking` 0 and has no entry.
- It runs only under the administrator's authorization sentinel, as every hop does.
- docs/migration-guide.md §5 gains its reverse recipe (drop both tables, drop the column, stamp the previous version), as that guide's §1a step 5 requires of every new version, with the statement copy checked by `TestDowngradeRecipe_MatchesGuide` (SR-16).

### SR-10.3: Retention
- `expire`'s delete and `agent-director-admin delete` remove a row's entries and claimable launches with the row, through the foreign keys.
- A reuse keeps the row's entries, which live as long as the row; it closes the running ones and deletes the claimable launches (SR-8.1).
- Cap: a row holds at most 300 entries, records and observations together (a fixed constant). A write that would add one more first deletes one entry, in its transaction, chosen in this order: the closed observation with the oldest `activity_at`; when no observation is closed, the closed record with the oldest `activity_at`; and only when nothing closed remains, the running entry with the oldest `activity_at`. Ties go to the lowest `created_seq`.
- A row holds at most 300 claimable launches (the same constant). A write that would add one more first deletes, in its transaction, the one with the oldest `opened_at`, ties to the lowest `created_seq`.

### SR-10.4: Upgrade safety
- Upgrading keeps every row and every field it had; no existing value is rewritten.

### SR-10.5: The `subagent_launches` table
- One row per open claimable launch, with: `created_seq` (the table's `INTEGER PRIMARY KEY AUTOINCREMENT`, as in `subagents`); `instance_id` (not null; a foreign key to the `spawns` row, `ON DELETE CASCADE`); `launch_token` (not null: the launch it was opened in); `tool_use_id` (not null); `subagent_type` (not null); and `opened_at` (integer milliseconds, not null: the launch request's receipt time). Nothing else: a claim copies no value (SR-4.5).
- Unique on (`instance_id`, `tool_use_id`), with an index that serves the claim (the current launch and type, oldest first) and the closes.
- `internal/store` is the only package that reads or writes it, and no verb reads it.

## SR-12: Never in the agent's way

### SR-12.1: Fail-open
- SubagentStart and SubagentStop write nothing on stdout, and the subagent work of PreToolUse, PostToolUse, [R+S] PostToolUseFailure and Stop adds nothing to it. Their only stderr output is a log line written through the hook logger's existing fallback: `newHookLogger` writes to stderr only when the config cannot be loaded, names no error log, or the error log cannot be opened, and with the default config every line goes to the error log. They inject no context, return no decision and never block a stop.
- They exit 0 on every failure: a config or store open failure, a store busy past its timeout, a failed write, a malformed or partial payload, and a payload over the hook's 1 MiB limit, which is dropped whole before it is parsed, as today (a `completed` result's content or a long `last_assistant_message` can reach that size).
- The 1 MiB limit is unchanged: no hook decodes a larger payload in part or as a stream. A foreground subagent's two stop signals both carry content (its SubagentStop's `last_assistant_message`, its `completed` result's `tool_response.content`); when both are over the limit, both are dropped, so its record stays `running` until a write of SR-8.1 closes it, and an entry that no claim confirmed never shows. A background subagent whose SubagentStop is dropped is closed by a later snapshot (SR-7.5). docs/hooks.md states the limit and links to docs/usage.md, which states what it means for a record (SR-16).
- A failed or dropped entry write changes nothing (its transaction rolls back, or never starts), logs one line with no content, and is repaired by the entry's next event, a later snapshot or liveness (SR-3.2, SR-3.3).
- No hook gains a sleep, a poll or a timeout of its own. The relayed PermissionRequest path is untouched.

### SR-12.2: The wait bound, and skipped transactions
- Claude Code waits for a hook before it goes on (F2 shows it for SubagentStart, which holds back the subagent's start). Each transaction of SR-3 waits for the store's write lock at most the store's busy timeout (`[store] busy_timeout_ms`, 10 s by default), as every hook write does today; a write still blocked then fails, is dropped (SR-12.1) and is repaired by reconcile. So SubagentStart and SubagentStop wait at most one busy timeout, and a hook of SR-3.3 at most one busy timeout more than it does today. That is the bound, of the kind today's hook writes already have, and it is accepted.
- A PreToolUse, PostToolUse or [R+S] PostToolUseFailure for a tool other than `Agent`, and a Stop carrying `agent_id`, open no entry transaction.
- A main-agent Stop skips its entry transaction when a plain read (no write lock) shows it can change nothing: its `background_tasks` lists no subagent, the current launch has no `running` `background` entry opened more than 2 s before the Stop's receipt time, and the row has no claimable launch opened more than 2 s before it. The read decides only whether the transaction runs; a skip can defer a close to a later Stop or to liveness, and never writes anything.

### SR-12.3: Performance
- Store work is added only to: SubagentStart and SubagentStop (newly registered: one transaction each, the row write with its entry writes); the launch request, the launch result and [R+S] PostToolUseFailure(Agent) (one transaction after the row write); a main-agent Stop (one plain read, and a transaction after the row write only when that read shows something to change); and the closing writes of SR-8.1 (their close, inside their own transaction). Every other hook does exactly today's store work.
- Each of these touches only one row's entries and claimable launches, and at most 300 of each (SR-10.3).
- `list_subagents` reads at most 300 entries of one row.
- Design only, checked in review and by no query-plan test: these reads and writes go through the indexes of SR-10.1 and SR-10.5.

## SR-17: Security, deployment, assumptions and dependencies

### SR-17.1: Security and authorization
- The hook gate is the authorization for every entry and claimable-launch write: only the row's recorded pane process can make one, and only for its own row (SR-3.1). No new privilege, credential, file, socket or network access is added.
- Both tables live in the existing store file, under its file mode. `list_subagents` needs what `get` and `list` need.
- No conversation content is stored (SR-5.2); a description is the launching call's short description, never prompt text (SR-6.1, SR-6.3).

### SR-17.2: Deployment
- It ships through the existing install and upgrade procedure. The schema hop runs only under the administrator's authorization sentinel (SR-10.2), and a store not yet migrated is refused as today.
- No configuration key is added. An agent running at the upgrade keeps working and stays untracked (`tracked` false) until its next launch (SR-9).
- The downgrade recipe reverses the hop (SR-10.2).
