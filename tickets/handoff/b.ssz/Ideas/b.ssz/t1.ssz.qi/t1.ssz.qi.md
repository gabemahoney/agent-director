# Codex support in agent-director

## Problem Statement

agent-director (AD) can only run Claude Code, so users who want OpenAI Codex agents run them outside AD with no state tracking, permission relay, strict kill or crash recovery. Codex differs from Claude in ways that would break AD's guarantees if launched like Claude: its usual launcher is not the real agent, it can share one background service between sessions, it reports in only at its first prompt, it stops at its own trust and hook-review dialogs, and its logins and rules live per folder. AD's own names and defaults also assume Claude.

## Goals

- **Feature parity.** A Codex agent under AD does exactly what a Claude Code agent under AD does today, on every surface. Where Codex cannot match, the difference is refused clearly or documented, never silent. Today's Claude behaviour settles every scope question.
- **No default agent, agent-generic names (breaking release).** Every spawn names its agent. Every Claude-specific name in AD's own surface (for example `claude_instance_id`, `claude_session_id`, `claude_args`) gets a generic name, with no aliases.

## This is a breaking release

AD's installer and upgrade change in this release. Unmigrated callers break; they are updated separately after release, without blocking it: CSCB and its bots, and the skills that drive AD (the Apiary skills configure_worktree, run-lanes and teardown_worktree; the user's installed copy of the install-agent-director skill (the skill's instructions in this repo are shipped product and are updated in this release); and the repair-orphaned-transcript skill, which stops working for all rows until then). The release notes say "breaking".

## Non-Goals / Out of Scope

- Any behaviour AD does not have for Claude today, for either agent: for example an initial-prompt input, launch-time checks of the agent program or its folder beyond today's, or showing a row's config folder.
- AD driving Codex as a headless background service instead of its interactive screen in tmux.
- Agent CLIs other than Claude Code and Codex, and a `list` filter by agent.
- AD enforcing `allow`, `deny` or `ask` for Codex, or creating, logging in, copying or cleaning Codex folders.
- Renaming Claude Code's own settings and variables; only AD's names change.
- Editing any `docs/*-guide.md` file, including adding a reverse (downgrade) recipe (a User-approved follow-up updates the guides after release, and also widens the doc guide's multi-account and hook/permission rows to cover Codex).

## Requirements

### Functional Requirements

**Choosing the agent.**
- Every spawn declares its agent, `claude` or `codex`, per call or through a template that names one. A per-call agent overrides the template's.
- A spawn with no agent and no agent-naming template is refused, as is any other agent value; `make-template` also refuses an unknown agent. Nothing is launched or written. No setting or environment variable supplies a default.
- Every row records its agent; `get` and `list` show it, as do their Go library and TS client equivalents. Rows from before the upgrade read `claude`.
- `resume` takes only the row id and reuses the row's agent, arguments and `extra_env`. A `reuse_finished` row takes its agent from its new spawn.

**Pass-through arguments.**
- Callers pass arguments through to Codex as they do to Claude today, per call and in templates. Per-call arguments belong to the spawn's agent and replace the template's; a template's arguments belong to the template's agent. On MCP and the Go library an explicitly empty list also replaces the template's; on the CLI and TS client an empty list counts as none, as today.
- A template that carries pass-through arguments must name its agent. A spawn that would inherit arguments from a template for a different agent is refused.
- A prompt among the pass-through arguments reaches the agent and is replayed by resume, as for Claude.
- As for Claude today, AD refuses Codex arguments overriding AD's per-launch settings (its hooks and their trust, and the settings its typing and question-tool rules rely on), picking or resuming another session, running non-interactively, or attaching to a remote or shared Codex service, with the refused-argument error Claude uses, naming the argument.
- Codex's own permission controls (sandbox, approvals, extra writable folders, bypass) and its hook-trust bypass pass through unchanged, as Claude's permission-skipping argument does.

**Groups, logins and environment.**
- As Claude groups share a config folder through `extra_env` today, a Codex group is a Codex home folder named with Codex's home variable in `extra_env`, directly or through a template. Agents in a group share that folder's login and rules, many may run on it at once, and agents in other folders do not get them.
- A Codex agent inherits its environment by exactly the rules a Claude agent does today. AD sets no Codex folder unless the spawn's `extra_env` or template names one, and never copies a parent's. A Codex spawned from inside an AD-launched Codex agent starts as a normal, separate agent.
- AD writes nothing into any Codex folder and never changes or ends a login. Folder trust and hook trust apply per launch only. `kill` and `expire` delete nothing in a folder.
- A Codex spawn whose call or template carries any `allow`, `deny` or `ask` entry is refused with an error pointing to the group's own Codex rules; the question-tool setting is not such an entry. `make-template` refuses a Codex template with any permission-list entry.

**Installing and launching.**
- AD's installer needs at least one of Claude Code or Codex. When Claude Code is absent it skips its Claude-only steps, says so when asked to register AD's MCP server with Claude, and turns help injection on unless the user opts out of hooks, as today.
- **Launch path per agent (approved exception to parity, the User, 2026-10-11).** AD's config gains an optional launch path for each agent. Unset, AD runs `claude` or `codex` from PATH, as today. Both are held to today's launcher rule: the program must be the agent itself or a wrapper that hands over to it. A program that breaks it (for example the npm `codex` launcher on PATH) leaves the row `pending`, noted `unreported`, as any such program does today; nothing is refused for an unset path and there is no new error. AD adds no other check of the program; a program that does not exist gives `missing`, as a missing Claude does today. The docs tell users who installed Codex with npm to set Codex's launch path to the real Codex program.
- AD's Codex agents never start or use a shared Codex background service; one already running is left alone. AD's own hooks always run in every Codex agent from its first event with no hook-review dialog, alongside the user's, group's and project's own.
- Pre-trust works as for Claude (`ok`, `skipped` or `failed`; `no_pre_trust` honoured for the row's life). An AD-launched Claude agent never stops for hook review, so for a Codex agent pre-trust also trusts that launch's hooks (the user's, the group's and the project's) for that launch only, writing nothing. `failed` and `no_pre_trust` leave the folder and the user's, group's and project's hooks untrusted. A group folder named with a non-absolute path gives `failed` and the launch proceeds.

**States.**
- Codex rows use Claude's states; Codex's interrupt (Esc mid-turn, or cancelling an approval) gives `waiting`. Only the agent's own report moves a row from `pending` to a live state, and Codex reports in at its first prompt.
- A Codex that runs but has not reported (no first prompt yet, a startup dialog or sign-in screen, or not meeting the launcher rule) stays `pending`, noted `unreported`.
- A session-end report for another session never ends a Codex row; Claude's rule is unchanged. After `/clear`, `/resume`, `/fork` or `/new` in a Codex agent, before or after its next prompt, `pause` still ends with the row `ended`, the row never reads `ended` while the agent goes on running afterwards (for example after `/new`, before its next prompt), and the row follows the new session.
- `ask_user` never appears for Codex rows. AD's question-tool setting, renamed, applies to both agents and is off by default; with it on, Claude rows never read `ask_user` either. With the question-tool setting on, a Codex agent cannot use its question tool even when its group's config turns it on, a Codex argument that turns the question tool on is refused, and the setting as it stands at resume applies to the replayed arguments; with it off, AD refuses nothing for it and leaves the tool as the group set it.
- Session ids, transcripts and `/clear` rotation work as for Claude, using Codex's real session id and transcript.

**Permission relay and typing.**
- With `relay_mode` on, every kind of Codex approval (shell commands, file edits, input to a running command, MCP tool calls, network access) opens a relayed request, and `decide` reaches Codex.
- The main agent's own interrupt counts as a turn end, as Claude's turn end does, and after an allow on a main-agent request the hold lasts until turn end. A Codex subagent's request, allowed or denied, keeps holding plain `send-keys` and `pause` until the agent ends, because Codex gives no proof that a subagent's tool ran.
- Requests show Codex's own tool names and inputs. Fields Codex does not send stay empty. `send-keys` submits at once, and multi-line text arrives as one prompt.

**Lifecycle, subagents and help.**
- Every AD verb, the admin tool, labels and the hook trail keep their Claude contracts for Codex rows, except where this PRD says otherwise. Codex rows report subagents through the b.xjn subagent view.
- With help injection on, a Codex agent gets AD's verb list at every session start (including after `/clear`) and after compaction. If Codex cannot re-add it after compaction, the docs record the difference.
- A Codex agent calling AD over MCP, with the documented setup, gets the right `parent_id` on agents it spawns, and they land on the same tmux server, as from a Claude caller. From a Codex agent's shell the AD CLI behaves as from Claude's wherever Codex's sandbox lets it reach AD; the docs say when it does not; MCP always works.

**Errors, renames and upgrade.**
- Each new refusal has a documented error name, also in the TS client: no agent, unknown agent, arguments not matching the agent, template with arguments but no agent, and permission list on Codex.
- The rename covers the CLI (admin tool included), MCP, Go library, TS client, config keys, template keys, trail fields, help text and user docs (README, `docs/`, and the Go library's and TS client's READMEs; not `docs/*-guide.md`).
- On the CLI, MCP and TS client an old name gets the existing invalid-input error, with a message naming the new name. An old key in config or a template gets the existing config or template error, naming the new key. No old name is silently dropped.
- The upgrade migrates stored rows, config files and stored templates to the new names, and writes `claude` into each stored template that names no agent. After the upgrade a template with no agent supplies none, and the spawn must name one. Old trail lines keep their old field names. The way back is: stop whatever starts agents, then every agent and every `serve`; put back the pre-upgrade copies of AD's store, config and templates; install the previous release and start the caller's previous version. The upgrade docs tell the operator to copy all three first.

**Documentation.**
- The README's prerequisites read "Claude Code or Codex (at least one)" and give Codex's rule (the rule it must meet, that Codex's npm launcher does not qualify, the minimum version, and that npm-installed Codex needs Codex's launch path set in AD's config). Its first spawn is one flow that works for both agents: name the agent and pass the first prompt in the arguments, then `list` the `waiting` rows, `read-pane` and `pause`.
- Every other doc item goes in the user doc the repo's doc guides assign it, with no new doc file; Codex material sits beside the Claude material it mirrors. Group folders go with the multi-account docs; Codex's hook and permission layering goes with the hooks, permissions and settings docs; symptoms and operator steps (bad group folders, a command still running after Esc) go in the error-case docs the guides name. The items:
  - Installing Codex (the qualifying install route only, as one command or link), and the symptoms of a missing, too-old or non-qualifying Codex, and of a group folder that is missing, not signed in, or under the system temp folder.
  - Spawning one, one example of answering a Codex approval at the pane, the tool names the relay shows, and what Codex's approval settings send to the relay.
  - The differences below, placed row by row per the doc guides, without the "Why" column.
  - Group folders: setup and login; an API-key login, set up once in the group folder; Codex takes no API key from `extra_env`; why a login must never be copied between folders (a copy can sign the original out); what still applies from outside a folder.
  - The manual steps to set up AD's MCP server and help per Codex folder (the default and each group folder).
- The architecture docs describe how AD runs Codex, and their "other agents unsupported" statement is updated. On every renamed surface (user docs, help text, error advice) wording is generic wherever it means either agent. Advice naming a folder variable names the variable of the agent the call is for: the spawn's per-call agent, else its template's; the row's for resume; the template's for make-template; both wherever no agent is known (help text, a spawn with no agent, a `make-template` with no agent).
- The build provides this release's breaking-change text: every old name with its new name, the required agent input, restarting any `serve` started before the upgrade, upgrading with this release's installer, and the way back. The releaser adds it at the top of the release notes with the version.

### Where Codex differs from Claude

The edge cases below add to this table.

| Difference | Why | What the user does |
|---|---|---|
| Permission lists refused | Codex takes no per-launch list | Use the group folder's Codex rules |
| An API key in `extra_env` does not sign Codex in | Codex reads its login only from its folder | Sign the group folder in once with the key |
| Report-in waits for the first prompt, even after resume (a resumed Claude row reads `waiting` at once), so, as for any `pending` row, `pause` and `send-keys` without `allow_pending` are refused until then | Codex reports in only at a prompt | Pass the first prompt in the arguments, or read the pane then type with `allow_pending`, per the caller contract |
| After `/clear`, `/resume`, `/fork` or `/new` the row shows the new session only from the next prompt | Codex reports the new session only when a prompt arrives | Nothing; `resume` before then uses the earlier session |
| Interrupt ends the turn; the hold after a main-agent allow lasts to turn end | Codex sends no turn end after an interrupt, nor proof a tool ran | Wait for turn end or answer at the pane |
| A subagent's approval, allowed or denied, holds plain `send-keys` and `pause` until the agent ends (Claude: only a denied one) | Codex sends no proof a subagent's tool ran | Look at the pane and send with its hash, or `kill` |
| A fallen-back allow never closes on its own when the tool runs | Codex sends no proof a tool ran | Record the pane answer |
| No automatic repair of a row left `working`; `find-missing`'s repair of a row stuck at `check_permission` always goes to `working` | Codex has no later idle signal after its turn end | Check the pane |
| Different pane keys and tool names | Codex's dialog and tools differ | See the docs |
| An npm-installed `codex` on PATH leaves the row `pending`, noted `unreported` | Codex's npm command is a launcher AD can't track | Set Codex's launch path in AD's config to the real Codex program |
| Codex caller needs MCP setup for `parent_id` | Codex passes little environment to MCP servers | Follow the documented setup |
| AD's CLI from a Codex agent's shell works only where Codex's sandbox lets it reach AD | Codex sandboxes its shell | Use MCP, which always works |
| Folder trust lasts one launch only: a later hand-run Codex in that folder asks for trust (Claude's pre-trust persists) | Trust is applied per launch | Answer Codex's trust prompt when running it by hand |
| The installer registers nothing with Codex | Codex keeps that setup in its folders | Follow the docs' manual MCP and help setup per Codex folder (the default and each group folder) |
| Some subagent fields unknown; a missed subagent stop stays running until the agent ends | Codex does not send them | Documented |

### Edge Cases and Error Handling

- **"Always allow" at a Codex pane** adds a rule to the whole group's folder. The docs say so, and that folders are not a security boundary against agents that can call AD.
- **A nested Codex started by hand** inside an AD agent's shell, or a shared Codex service: their reports move no row.
- **Esc while a command runs:** Codex keeps the command running in the background while the row reads `waiting`. The docs say so, what happens to that command when the row is paused or killed, and what the operator does.
- **Codex's question tool turned on in a group's config with the question-tool setting off:** the row reads `working` while the question waits. The docs warn of it.

### Non-Functional Requirements

- **b.fmk guarantees** hold for Codex rows without loosening: only the row's own agent moves the row, the label proof, strict kill and process-only liveness.
- **No screen text** is read to detect any state, dialog or prompt.
- **Hooks fail open** for Codex, except the relayed permission path, which stays fail-closed as for Claude.
- **Performance:** a Codex spawn or resume completes within today's client time limits. The docs say a first start on a new folder can be slower.
- **Upgrade-safe:** every row, config setting and template survives the upgrade with its data.
- **Platforms:** every AD host on which Codex runs; AD's supported hosts do not change.
- **Testing safety:** tests never touch the user's real AD data or Codex folders and never sign the user out. Before release, the Codex acceptance criteria are checked against a real Codex in a throwaway environment, using a login the User provides.

## Assumptions

- This builds on AD's current release line with b.kdf's `unreported` note; b.146's relay work is merged before this work.
