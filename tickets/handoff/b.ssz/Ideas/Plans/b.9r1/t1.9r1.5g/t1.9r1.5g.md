# Epic 6: the pre-release real-Codex check passes on the newest and the minimum Codex

## Outcome
Before release, every Codex acceptance criterion and every research item is checked again against a real Codex in a throwaway container, on both the newest Codex and the documented minimum. Every answer that changes code or docs is fixed with its tests re-run, and nothing SR-16.3 forbids is left: no RN unanswered, no "stop and ask" unresolved, the b.xjn-gated parts settled by the SR-6.8 addendum (approved 2026-10-12) and built in Epic 5.

## Depends on
Epics 2, 3, 4 and 5. Its b.xjn gate reduces to its dependency on Epic 5. It uses the box's `~/.codex` login under Epic 1's rules (decided by the User; not blocked on the User).

AC numbers below are the PRD's and SRD Appendix C's (renumbered 2026-10-12; this Epic was one lower from AC-13 on).

## Scope (SR-16.2, SR-16.3, AC-28)
- **Isolation and login, as in Epic 1.** A local throwaway container on this box, never the host and never the job scheduler (it forbids secrets): its own HOME, Codex folders, tmux server and AD store, with AD installed in it by this release's `install.sh`; Codex's sandbox running, so file-edit and network approvals are exercised. The box's `~/.codex/auth.json` (ChatGPT login, Codex 0.159.2) is copied into the running container at run time only, never into a build context, image, ticket, log, report or the repo; a sign-out of that login is acceptable. AC-9's "same account" evidence is taken inside the container (the folder AD used is still signed in at the end of the run, before the container is removed).
- **Two runs, both required:** the newest Codex available, and the documented minimum (0.156.0, or the later version RN-17 found). If the minimum cannot be installed, the documented minimum is raised to the oldest version the check ran (README, `docs/install.md`).
- **Each run checks** the real-Codex halves of AC-6 to AC-24 and AC-28. That includes:
  - AC-12 with a hook the user's or group folder's config already trusts, which runs with no review dialog under `no_pre_trust` (RN-23);
  - two agents on one folder and an agent on another (AC-7);
  - every approval kind relayed (AC-18);
  - a Codex caller over MCP (AC-23);
  - AC-21 as amended. After a real Codex subagent has run (the probe's mock model can drive one, as RN-8's runs did), `list-subagents` on the row reports `tracked` false and `subagents` `[]`. This replaces the void "Codex subagents in the subagent view" check.
- **Every RN rechecked** (RN-1 to RN-24). SR-2.3's two constant lists compared with both versions' help and updated. `ResumeArgs` and Claude's option table (SR-6.8.9) compared with both agents' parsers at the documented minimum (Claude 2.1.280, Codex 0.156.0) and the newest version, and updated (SR-16.2 as amended). The hook-trust golden data re-captured on the newest Codex, and `internal/spawn/testdata/` updated if it changed. Its SubagentStart and SubagentStop entries may stay as captured: AD composes none for Codex.
- **The way back once:** upgrade an install of the previous release (its directory, store, config and templates) with this release's installer, take the way back, install the previous release, and see its `list` read the old rows.
- **Results** under `tickets/Ideas/b.ssz/prerelease/`: versions, commands, and each AC's and RN's result.
- **Fixes (SR-16.3).** Every code or doc item an answer changes is fixed in this Epic, with the unit, real-tmux, installer and affected Docker tests re-run in the sandbox. A "stop and ask" goes to the User and holds the release.
- **Ready for the releaser.** The breaking-change text is complete (every old name; b.xjn adds none; the required agent; the reuse and resume rule (a reuse may change the agent; only a switch starts a new life; resume continues the last agent's latest session, never across a switch; every SR-6.8.7 meaning change); the directory move; restarting `serve`; upgrading with this installer; the way back); the TypeScript version floor is this release's version; this work's hop version is re-checked against dev/v0.12.0 before the merge (SR-3.2). Cutting and publishing the release stays with the releaser.

## Carry note 2026-10-12: a memory-consolidation thread's SessionStart (from the SR-6.8 addendum review)
Add one live check to each run, newest and minimum Codex.

- **The check.** Turn Codex's `memories` feature on (it is off by default), in the container's Codex folder or with `--enable`. Let it run a memory-consolidation thread under an AD-launched Codex agent. Then see whether AD's per-launch hooks reach that thread.
- **Why.** From Codex's 0.162.1 source:
  - A memory-consolidation thread is an internal session, not a subagent. Its config is a clone of the session's (`memories/write/src/phase2.rs`), so it likely carries AD's `-c hooks` entries.
  - Codex sends it a plain **SessionStart**, not SubagentStart. Only its Stop filters out per-launch hooks.
  - If AD's SessionStart hook runs for it, the hook passes the gate (same Codex process). The payload carries the thread's own session id and no `agent_id`, so SR-6.4 would switch the row to that session. Its UserPromptSubmit or tool hooks, if any, could also leave the row `working`.
  - Not run live: the probe never had `memories` on. SR-6.8.1 C5 (no SubagentStart or SubagentStop from such a thread) holds either way. This check is about SessionStart and the other unmarked hooks.
- **What to record** in `tickets/Ideas/b.ssz/prerelease/results.md`:
  - which AD hooks fire for the thread, and with what `session_id` and `agent_id`;
  - whether the row's session id, transcript path or state changes.
- **If not as assumed.** If any AD hook moves the row (rotation, `working`, a session change), stop and ask the User before release, as for RN-8's unmarked `/review` thread. Recommended answer: a docs difference ("with Codex's `memories` feature on, the row can follow a memory thread's session"), unless the change is user-visible enough to need a code rule. Any code rule that changes what moves a row needs a TLA+ run first (SR-12).
