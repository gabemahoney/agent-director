## Driver mode

All cases below are written for `DRIVER_MODE=shell` — the orchestrator
runs the harness with `make test-docker EPIC=epic-03-spawn`. Each t2
body has a single fenced ` ```bash ` block the driver executes after
the per-case DB-reset fixture.

The hook cases (`spawn-1`, `spawn-2`, `spawn-3`, `spawn-9`) synthesise
hook payloads rather than launching a real Claude — this keeps the
harness API-free for the gate run and exercises exactly the SRD §5.2
mapping without any cross-contamination from Claude Code's own
internals.

A hook moves a row only when the `agent-director hook` process is a
direct child of the row's recorded pane process (SR-22.9), so these
cases never pipe a hook from the case's own shell (such a hook is
ignored as `pid_mismatch` and leaves the row as it was). Instead
(SR-20.9):

- The spawn runs as `PATH=/opt/driver/stand-in-claude:$PATH
  agent-director spawn …`. tmux looks `claude` up on the PATH of the
  process that runs the create (it replaces the session's PATH with the
  client's, so `--extra-env PATH=…` would still start the real Claude
  Code), and finds the stand-in `claude`
  (`test/driver/stand-in-claude/claude`) first; it ignores its arguments
  and `exec`s `bash --noprofile --norc -i`, so an interactive shell is
  the pane process agent-director records. A `resume` that should launch
  the stand-in needs the same prefix.
- `/opt/driver/pane-hook.sh <id> '<payload json>'`
  (`test/driver/pane-hook.sh`) writes the payload to a file, reads the
  row's `pane_id` and `tmux_socket` with a read-only `sqlite3` SELECT,
  and types `agent-director hook < <file> > <out> 2> <err>; echo $? > <rc>`
  into the pane with `tmux send-keys -l --` and Enter: simple commands,
  so the pane's bash forks the hook directly. It waits (bounded) for
  `<rc>`, prints the hook's stdout and exits with the hook's exit
  status. `--no-wait` / `--wait <job dir>` split the send from the wait
  for a hook that blocks (relay); `--env KEY=VALUE` prefixes the typed
  command; `--pane <target>` types into another pane.

## tmux session sweep

Cases that spawn (`spawn-1`, `spawn-2`, `spawn-3`, `spawn-7`, `spawn-8`,
`spawn-9`) leave tmux sessions under the `cd-*` prefix. The DB-reset fixture kills
`cd-*` sessions between cases (see `test/driver/db-reset.sh`), so
cases never see each other's leftovers.

The rejection cases (`spawn-12`, `spawn-13`, `spawn-14`) expect no
session at all; `spawn-19` makes its own leftover session. They use names outside the `cd-*` prefix, so each one
records the live tmux session ids first and, on exit, kills any session
that was not there before (by its `$N` id). A regression therefore
fails the case without leaking a session into later cases.

`spawn-20` makes its own leftover under a `cd-` name (the pending row's
recorded name), so the next reset sweeps it too; it still records the
live session ids first and kills any new session by its `$N` id on exit.
